# Spring Boot Custom Validation — Revision Notes

## 1. The Core Problem: `IllegalStateException: Invalid target for Validator`

**Root cause:** A custom `Validator` was registered globally via `@InitBinder`, but its `supports()`
method only accepted the *nested* type (e.g. `NewUser`), while Spring was invoking it against the
*wrapper* DTO bound at the controller (e.g. `CreateUserRequest`).

```java
@InitBinder
public void initBinder(WebDataBinder binder) {
    binder.addValidators(newUserValidator); // fires for EVERY @Valid target in scope
}
```

When `@Valid @RequestBody CreateUserRequest body` is bound, Spring runs **every** validator
registered on the binder against the target. If `supports(CreateUserRequest.class)` returns
`false`, Spring throws — it does not silently skip.

**Key gotcha:** this isn't per-type-scoped. If you register multiple validators
(`createUserRequestValidator`, `updateUserRequestValidator`) globally, an `UpdateUserRequest`
call will *also* try to run the create-validator and throw, since it fails `supports()`.

---

## 2. Why the Generated-Controller (OpenAPI Delegate) Pattern Makes This Worse

With OpenAPI-generated interfaces, you can't edit the controller signature:

```java
default ResponseEntity<UserResponse> createUser(
    @Valid @RequestBody CreateUserRequest body
) {
    return getDelegate().createUser(body);
}
```

You can't add a `BindingResult` parameter or change what gets bound. This pushes toward
**manual validation in the delegate implementation** rather than fighting Spring's automatic
binder-validation plumbing.

---

## 3. Industry-Standard Approach

### a) Field-level checks → Bean Validation annotations on the generated model
`@NotBlank`, `@Email`, `@Size`, etc. on `NewUser`/`UpdateUser`. These run automatically via
`@Valid` + Hibernate Validator (`LocalValidatorFactoryBean`), cascading into nested objects if
the generator emits `@Valid` on the nested field (`useBeanValidation: true`).

### b) Business-rule checks (uniqueness, cross-field, DB lookups) → manual validator call in the delegate
Not wired through `@InitBinder`. Called explicitly:

```java
@Override
public ResponseEntity<UserResponse> createUser(CreateUserRequest body) {
    NewUser user = body.getUser();
    BeanPropertyBindingResult errors = new BeanPropertyBindingResult(user, "newUser");
    newUserValidator.validate(user, errors);
    if (errors.hasErrors()) {
        throw new RequestValidationException(errors);
    }
    ...
}
```

This avoids `supports()` mismatches entirely, since you're calling `validate()` directly on the
exact type the validator expects — no dispatch ambiguity.

**Alternative (if you must keep the global `@InitBinder`):** use one composite/dispatcher
validator whose `supports()` accepts all wrapper types and branches internally by
`instanceof`, so only one validator is ever registered on the binder.

## 4. `BeanPropertyBindingResult`

- Concrete implementation of Spring's `Errors`/`BindingResult` interface.
- Just an empty "notebook" for validation results — constructing it does **not** validate
  anything by itself. You must call `validator.validate(target, errors)` to populate it.
- Constructor: `new BeanPropertyBindingResult(target, objectName)` — `objectName` is just a
  label used in error reporting, not functionally significant elsewhere.
- Needed here because you're bypassing Spring's automatic binder flow (no `@Valid` +
  `BindingResult` method-parameter pair available on a generated controller), so you build the
  container yourself.

### How `@Valid` + `BindingResult` works automatically (hand-written controllers)
```java
public ResponseEntity<?> foo(@Valid @RequestBody SomeDto dto, BindingResult result) { ... }
```
- `@Valid` triggers `WebDataBinder.validate()`, which runs **every** validator in the binder's
  list (default: just the JSR-380 `LocalValidatorFactoryBean`, annotation-driven).
- `BindingResult` must be the parameter **immediately after** the `@Valid` argument — Spring
  checks this positionally. If present, errors are captured instead of thrown. If absent,
  Spring throws `MethodArgumentNotValidException` automatically.

## 5. Exception Design

**Don't reuse `jakarta.validation.ValidationException`** — it's a generic Bean Validation spec
class with only `String`/`Throwable` constructors; it can't carry a Spring `Errors` object.

Define a custom exception instead:

```java
public class RequestValidationException extends RuntimeException {

    private final Map<String, List<String>> fieldErrors;

    public RequestValidationException(Errors errors) {
        super("Validation failed for object: " + errors.getObjectName());
        this.fieldErrors = errors.getFieldErrors().stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                fe -> List.of(fe.getDefaultMessage())
            ));
    }

    public Map<String, List<String>> getFieldErrors() {
        return fieldErrors;
    }
}
```

> Note: `Collectors.toMap` throws on duplicate keys (two errors on the same field). Only add a
> merge function (`(a, b) -> a`) if that's actually possible for your validators.

Wire it into the existing `GlobalExceptionHandler`:

```java
@ExceptionHandler(RequestValidationException.class)
public ResponseEntity<GenericErrorModel> handleRequestValidation(RequestValidationException ex) {
    GenericErrorModel error = new GenericErrorModel(ex.getFieldErrors());
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
}
```

Keeping validation errors centralized in one advice class gives a **uniform error response
shape** (`GenericErrorModel`) regardless of whether the failure came from annotations, custom
validators, or business exceptions (`DuplicateIdException`, auth, etc.).

## 6. 400 vs 422 for Validation Failures

| Code | Meaning | When |
|---|---|---|
| **400 Bad Request** | Malformed at the syntax level, or general catch-all for client error | Broken JSON, wrong content-type; many teams also use it for *all* client input problems, including validation |
| **422 Unprocessable Entity** | Well-formed and understood, but semantically invalid | JSON parses fine, but content fails business rules (e.g. bad email format, duplicate username) |

- Spec-purists use 422 for validation; many production APIs and Boot's own defaults use 400
  for everything.
- **If targeting RealWorld/Conduit spec compatibility**, the reference spec documents `422` for
  registration/update validation errors — relevant if a stock RealWorld frontend needs to work
  against this backend unmodified.
- Final call: **400**, per your decision — simpler mental model (4xx client error → 400 unless a
  more specific code clearly fits), and acceptable outside strict spec-conformance requirements.

## 7. Java Records (side note)

A `record` is an immutable data-carrier class (Java 16+). Compiler auto-generates constructor,
accessors (`field()`, not `getField()`), `equals()`, `hashCode()`, `toString()`.

```java
public record FieldErrorDetail(String field, String message) {}
```

- Good fit: small internal value objects, tuple-like return values, things constructed once and
  never mutated.
- Not a fit for generated OpenAPI models (`NewUser`, `CreateUserRequest`) — those need mutable
  setters for Jackson deserialization.
