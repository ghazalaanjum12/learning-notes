## 1. Maven & Spring Boot Project Structure

### spring-boot-starter-parent
Declared at the top of your `pom.xml`. It is the parent POM that provides:
- **Dependency version management** — no need to specify versions for common libraries. Spring Boot pins compatible versions of Jackson, Hibernate, Tomcat etc.
- **Plugin configuration** — Maven compiler plugin pre-configured with Java version and encoding
- **Resource filtering** — `application.properties` / `application.yml` automatically included

```xml
<parent>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.2.0</version>
</parent>
```

### Maven Wrapper Files
When you create a Spring Boot project you will see these files:

| File/Folder | Purpose |
|---|---|
| `.mvn/` | Contains wrapper config — specifies which Maven version to download |
| `mvnw` | Shell script for Mac/Linux to run Maven via the wrapper |
| `mvnw.cmd` | Same but for Windows |

**Should you commit these?** Yes — always. Their purpose is to ensure everyone on the team uses the same Maven version without needing Maven installed globally.

### What to put in .gitignore
```
target/       ← compiled output, never commit
*.class
.idea/        ← IDE specific files
*.iml
```

Never commit the `target/` folder — it is generated output that anyone can reproduce by running `mvn clean install`.

### Standard Project Structure
```
com.example
    ├── MyApplication.java        ← main class here (root package)
    ├── controller
    │     └── UserController.java
    ├── service
    │     └── UserService.java
    └── repository
          └── UserRepository.java
```

Keep your main class in the **root package**. Spring Boot scans the root package and all subpackages automatically — no extra config needed.

### Component Scanning
`@SpringBootApplication` tells Spring where to scan for annotated classes (`@RestController`, `@Service`, `@Repository` etc.) and register them as beans.

If your structure is non-standard you can specify explicitly:
```java
@SpringBootApplication(scanBasePackages = "com.example")
public class MyApplication {
    public static void main(String[] args) {
        SpringApplication.run(MyApplication.class, args);
    }
}
```

Spring scans for:
- `@Component`
- `@Controller` / `@RestController`
- `@Service`
- `@Repository`

Without scanning the right package, your controllers are just plain Java classes — Spring never registers them, no endpoints get mapped, you get 404s.

## 2. Spring Boot Starters

Starters are **dependency aggregators** — thin POMs that pull in a curated group of related libraries with a single dependency declaration.

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
    <!-- No version needed — parent manages it -->
</dependency>
```

> **Note:** `spring-boot-starter-web` is deprecated in favour of `spring-boot-starter-webmvc` as of Spring Boot 4.x.

### Common Starters

| Starter | What it bundles |
|---|---|
| `spring-boot-starter-webmvc` | Spring MVC, embedded Tomcat, Jackson |
| `spring-boot-starter-data-jpa` | Hibernate, Spring Data JPA, transactions |
| `spring-boot-starter-security` | Spring Security |
| `spring-boot-starter-test` | JUnit 5, Mockito, AssertJ |

### One-line mental model
- `starter-parent` = version manager + build defaults
- `starter-*` = pre-packaged dependency bundles
- `starter-webmvc` = everything you need to serve HTTP requests, zero manual wiring

## 3. Web Server vs Application Server

### The historical split

| Type | Examples | Job |
|---|---|---|
| Web server | Nginx, Apache HTTP | Handles raw HTTP, serves static files (HTML, CSS, images). Fast and lightweight but has no idea what Java is. |
| Application server | Tomcat, JBoss | Knows Java, runs your business logic, handles the Servlet lifecycle |

### Classic production setup
```
Internet → Nginx (web server) → Tomcat (app server) → Your Java code
```

Nginx handles the flood of HTTP traffic and forwards only dynamic requests to Tomcat.

### In Spring Boot locally
Embedded Tomcat does **both jobs**. There is no separate Nginx. Tomcat receives HTTP directly and passes it to your code.

### "Server" is just a role, not hardware
The word "server" means *"something that listens for requests and serves responses."* All of these can run on the same laptop. In production, companies put them on separate machines for performance — but that is a deployment decision, not a requirement.

| What people say | What they mean |
|---|---|
| "The server is down" | Physical machine crashed |
| "Web server" | Software listening for HTTP |
| "Application server" | Software running business logic |

## 4. Tomcat — The Servlet Container

### What Tomcat actually does
HTTP is just **text travelling over a network**. A raw HTTP request looks like:

```
GET /users/42 HTTP/1.1
Host: localhost:8080
Accept: application/json
```

Your Java code cannot work with raw strings. **Tomcat translates this into Java objects** — specifically `HttpServletRequest` and `HttpServletResponse` — defined by the Java Servlet specification.

Tomcat is called a **servlet container** because it contains and manages your servlets. It implements the Servlet API contract.

### Tomcat's translation job
```
Raw HTTP text arrives
      ↓
Tomcat parses it → creates HttpServletRequest object
      ↓
Passes it to Spring's DispatcherServlet
      ↓
DispatcherServlet routes to your @RestController
      ↓
Your method runs and returns a result
      ↓
Tomcat serializes response back to raw HTTP text
      ↓
Sends over the network
```

### Embedded vs External Tomcat
- **Traditional Spring MVC** — deploy a WAR file to an externally installed Tomcat
- **Spring Boot** — Tomcat is embedded inside your JAR, starts up within your process when you run the app

## 5. Jackson — JSON Serialization

Jackson operates at a **different level than Tomcat**. Think of an HTTP request as a letter in an envelope:

```
[Envelope — HTTP structure]
POST /users HTTP/1.1
Host: localhost:8080
Content-Type: application/json

[Letter inside — the body]
{"name": "Ghazala", "age": 30}
```

- **Tomcat** handles the **envelope** — parses HTTP structure into `HttpServletRequest`. Treats the body as raw bytes.
- **Jackson** handles the **letter** — converts JSON body into a Java object and vice versa.

### What Jackson does
```java
// Jackson converts this JSON:
{"name": "Ghazala", "age": 30}

// Into this Java object automatically:
User user = new User();
user.setName("Ghazala");
user.setAge(30);
```

And on the way out — when your controller returns a `User` object, Jackson converts it back to JSON before Tomcat sends it.

### One line each
- **Tomcat** = translates HTTP structure (envelope) ↔ Java
- **Jackson** = translates JSON content (letter) ↔ Java objects

## 6. Spring MVC Request Lifecycle

### Full picture
```
Raw HTTP request arrives
        ↓
Tomcat → parses envelope → HttpServletRequest
        ↓
Spring's DispatcherServlet → routes to correct @RestController
        ↓
Jackson → parses JSON body → Java object (@RequestBody)
        ↓
Your method runs, returns a Java object
        ↓
Jackson → converts Java object back to JSON
        ↓
Tomcat → wraps in HTTP response → sends over network
```

### Key annotations

| Annotation | Purpose |
|---|---|
| `@RestController` | Marks class as controller + adds `@ResponseBody` to all methods. Takes **no path**. |
| `@RequestMapping("/path")` | Sets the **base path** for all endpoints in the class |
| `@GetMapping("/path")` | Maps a specific GET endpoint |
| `@RequestBody` | Tells Spring to give the request body to Jackson for deserialization |
| `@ResponseBody` | Tells Spring to give the return value to Jackson for serialization (included in `@RestController`) |

### Common mistake
```java
// WRONG — @RestController does not accept a path
@RestController("/test")
public class TestController { }

// CORRECT
@RestController
@RequestMapping("/test")
public class TestController { }
```

## 8. OpenAPI Specification

### What it is
OpenAPI describes an HTTP-based API in a machine-readable document. It covers endpoints, parameters, request/response bodies, status codes, authentication, and data models.

> "HTTP-like API" — OpenAPI covers any API that communicates over HTTP, not just strict REST. This includes REST-ish APIs and RPC-style-over-HTTP.

### Key sections

#### servers
The base URL prepended to all endpoint paths:
```yaml
servers:
  - url: https://api.example.com/api
    description: Production
  - url: http://localhost:8080/api
    description: Local development
```

#### tags
Group related endpoints for organization. In Swagger UI they create collapsible sections. In code generation they determine which interface an endpoint goes into:
```yaml
paths:
  /users:
    get:
      tags:
        - Users
      summary: Get all users
```

Maps to:
```
Tag: Users     → generates UsersApi interface → you implement UserController
Tag: Articles  → generates ArticlesApi interface → you implement ArticleController
```

#### operationId
Unique identifier for an endpoint. Used by code generators to name the method:
```yaml
/users/login:
  post:
    operationId: Login   ← generated method will be named login()
```

Without it the generator invents ugly names like `usersLoginPost()`.

#### x- vendor extensions
The `x-` prefix means a custom field not in the official spec but recognised by specific tools:
```yaml
x-codegen-request-body-name: body  ← names the request body parameter in generated code
```

Find supported extensions in the documentation of whichever tool consumes your spec (e.g. https://openapi-generator.tech/docs/generators/spring).

### Code generation workflow
```
openapi.yaml (source of truth)
      ↓ mvn clean install
Generated interfaces in target/generated-sources/   ← do not commit
      ↓ you implement
Your controllers in src/main/java/
```

Use `interfaceOnly: true` so the generator creates interfaces, not concrete classes:
```xml
<configOptions>
    <interfaceOnly>true</interfaceOnly>
    <useSpringBoot3>true</useSpringBoot3>
</configOptions>
```

Then implement:
```java
@RestController
public class UserController implements UsersApi {

    @Override
    public ResponseEntity<User> getUserById(Long id) {
        // your implementation
    }
}
```

If the spec changes, regenerate and the compiler tells you exactly what needs updating.

### Where to place your spec
```
src/main/resources/
    ├── application.properties
    └── openapi/
          └── openapi.yaml
```

### securitySchemes
```yaml
components:
  securitySchemes:
    basicHttpAuthentication:
      type: http
      scheme: Basic
    bearerHttpAuthentication:
      type: http
      scheme: Bearer
      bearerFormat: JWT   ← hint that the token is a JWT specifically
```

## 9. HTTP Methods

### Common methods

| Method | Purpose |
|---|---|
| GET | Retrieve a resource |
| POST | Create a resource |
| PUT | Replace a resource |
| PATCH | Partially update a resource |
| DELETE | Delete a resource |
| HEAD | Same as GET but returns **no body** — only headers |
| OPTIONS | Ask server what methods are supported for an endpoint |

### HEAD
Used to check metadata without downloading content:
```
HEAD /files/largefile.zip
→ Returns Content-Length, Content-Type, Last-Modified — no body
```

### OPTIONS
You will encounter this constantly via **CORS preflight**. When a React frontend on `localhost:3000` calls your API on `localhost:8080`, the browser automatically sends an OPTIONS request first asking if that cross-origin request is allowed. Spring and your CORS config handle this — you rarely implement it manually.

## 10. API vs Endpoint

| Concept | Definition | Analogy |
|---|---|---|
| API | The entire interface your application exposes — all endpoints, auth rules, error formats, data models | The whole restaurant menu |
| Endpoint | A single URL + HTTP method combination | One dish on the menu |

### Example
Your application exposes a **User Management API** containing these endpoints:
```
GET    /users          → get all users
GET    /users/{id}     → get one user
POST   /users          → create a user
DELETE /users/{id}     → delete a user
```

### APIs within one application
A single Spring Boot app can have logically grouped APIs:
- **User Management API** → `/users/**` → `UserController`
- **Orders API** → `/orders/**` → `OrderController`

Technically one API (one running app), but people group them loosely by domain for clarity. They become truly separate APIs only in a microservices architecture where each runs as its own process.

## 12. HTTP Communication Patterns

### Webhook
A **one-way HTTP callback**. Not a new protocol — just a regular HTTP POST request. A pattern/convention where you give a third party your URL and they call it when something happens.

```
Stripe payment event occurs
      ↓
Stripe sends POST to your URL: https://yourapp.com/webhooks/stripe
      ↓
Your app updates order status
```

Implementing a webhook receiver in Spring Boot:
```java
@RestController
public class StripeWebhookController {

    @PostMapping("/webhooks/stripe")
    public ResponseEntity<Void> handleStripeEvent(@RequestBody String payload) {
        // handle the event
        return ResponseEntity.ok().build();
    }
}
```

### Server-Sent Events (SSE)
Server pushes updates to a **browser** over a persistent HTTP connection. One way — server to browser only.

Use cases: live order status, news feeds, notifications.

### WebSocket
A **persistent two-way connection** between client and server. Starts as HTTP then upgrades to the WebSocket protocol (`ws://`).

Use cases: chat, collaborative editing, live sports scores.

### Comparison

| | Webhook | SSE | WebSocket |
|---|---|---|---|
| Who talks to whom | Server → Server | Server → Browser | Server ↔ Browser |
| Direction | One way | One way | Two way |
| Protocol | HTTP POST | HTTP (streaming) | WebSocket (ws://) |
| Connection | Closes after each call | Stays open | Stays open |
| Use case | Payment notifications, CI/CD triggers | Live feeds | Chat, collaboration |

### Mental model
- **Webhook** = server talks to server
- **SSE** = server talks to browser, one way
- **WebSocket** = server and browser talk to each other, two way

## 13. HTTP Authentication

### The two headers

**`WWW-Authenticate`** — sent by the **server** on 401 to tell the client what it expects:
```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
```

**`Authorization`** — sent by the **client** with credentials:
```
GET /users
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

The scheme identifier (Basic, Bearer) tells the server how to interpret the credentials. That is literally all HTTP authentication is at the protocol level — everything else (JWT, OAuth, OIDC) is implementation detail on top.

### Types

#### Basic Authentication
Username and password Base64 encoded. Not encrypted — only safe over HTTPS. Rarely used in modern APIs.
```
Authorization: Basic Z2hhemFsYTpwYXNzd29yZA==
```
(That is just `ghazala:password` in Base64)

#### Bearer + JWT
Most common in modern REST APIs. A JWT sent with every request:
```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

#### API Key
A static key identifying the calling application. Not formal HTTP auth but commonly sent as a header:
```
x-api-key: a7f3d9c2-4b1e-4f8a-9c3d-2e5f7a1b6c4d
```

Used for server-to-server communication — identifies the **application**, not the user.

#### OAuth 2.0
Delegated authorization framework — used for "Login with Google/GitHub" flows. See [OAuth 2.0 section](#15-oauth-20).

### Summary

| Type | Used for |
|---|---|
| Basic | Legacy systems |
| Bearer + JWT | Modern REST APIs, user login |
| API Key | Server to server, identifying applications |
| OAuth 2.0 | Delegated access, social login |

## 14. JWT (JSON Web Token)

### The problem JWT solves
Without JWT you need a DB lookup on every request to validate a session. JWT makes tokens **self-verifiable** — no DB needed.

### Structure
A JWT is three Base64 encoded strings separated by dots:
```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJnaGF6YWxhIn0.abc123
      HEADER                   PAYLOAD            SIGNATURE
```

#### Header
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```
Specifies the signing algorithm.

#### Payload (Claims)
```json
{
  "sub": "ghazala",
  "role": "admin",
  "exp": 1234567890
}
```
Facts about the user. **Not encrypted** — just Base64 encoded. Never put passwords or sensitive data here.

#### Signature
```
HMACSHA256(
    Base64(header) + "." + Base64(payload),
    secretKey
)
```
The server takes the header and payload, runs them through a hashing algorithm with a **secret key only the server knows**, and appends the result.

### Verification
When the client sends the JWT back:
1. Server takes the header and payload from the incoming token
2. Runs them through the same algorithm with the same secret key
3. Compares result to the signature in the token
4. If they match → valid. If someone tampered with the payload → different hash → mismatch → 401

```
Tampered payload → different hash → signature mismatch → 401 Unauthorized
```

### Analogy
Think of the signature like a **wax seal on a letter**. Only the king has the seal. If someone opens and changes the letter, the seal is broken. The secret key is your seal — only your server has it.

### HS256 vs RS256

| | HS256 | RS256 |
|---|---|---|
| Type | Symmetric | Asymmetric |
| Signing | Same secret key signs and verifies | Private key signs, public key verifies |
| Use case | Single server | Microservices, multiple verifiers |
| Risk | Secret must be shared to verify | Public key is safe to share |

### Full login flow
```
1. POST /users/login with username + password
2. Server validates credentials against DB
3. Server creates payload: { sub: "ghazala", role: "admin", exp: ... }
4. Server signs with secret key → JWT
5. JWT returned to client
6. Client stores JWT
7. Every subsequent request: Authorization: Bearer <JWT>
8. Server verifies signature — no DB needed
9. Server reads payload to know who the user is
```

### In Spring Boot (using jjwt library)
```java
// Creating a token on login
String token = Jwts.builder()
    .setSubject("ghazala")
    .claim("role", "admin")
    .setExpiration(new Date(System.currentTimeMillis() + 86400000))
    .signWith(secretKey, SignatureAlgorithm.HS256)
    .compact();

// Verifying on each request
Claims claims = Jwts.parserBuilder()
    .setSigningKey(secretKey)
    .build()
    .parseClaimsJws(token)
    .getBody();

String username = claims.getSubject(); // "ghazala"
```

### Token formats

| Format | Structure | Verification | Common use |
|---|---|---|---|
| JWT | header.payload.signature | No DB needed | Modern REST APIs |
| Opaque | Random string | DB lookup required | Session tokens, OAuth |
| SAML | XML | XML validation | Enterprise SSO |

## 15. OAuth 2.0

### Core idea
OAuth 2.0 is about **delegated access** — a user grants a third party app limited access to their account without giving it their password.

### Four players
- **Resource Owner** — the user
- **Client** — the app wanting access
- **Authorization Server** — issues tokens (Google, GitHub, your own)
- **Resource Server** — the API holding the user's data

> **Important:** OAuth 2.0 does not mandate a token format. Access tokens can be JWT or opaque — it is a choice, not a requirement.

### Grant Types (Flows)

#### 1. Authorization Code Flow
Most common and most secure. For web apps with a backend.

```
User clicks "Login with Google"
        ↓
App redirects to Google's login page
        ↓
User logs in and grants permission
        ↓
Google redirects back with a short-lived CODE
        ↓
Your backend exchanges code for access token (server to server — token never in browser)
        ↓
Backend uses access token to call Google APIs
```

#### 2. Authorization Code + PKCE
For mobile apps and SPAs with no backend. PKCE (Proof Key for Code Exchange) ensures the entity exchanging the code is the same one that requested it:

```
App generates code_verifier (random string)
        ↓
Hashes it → code_challenge
        ↓
Sends code_challenge with auth request
        ↓
Receives authorization code
        ↓
Exchanges code + original code_verifier for token
        ↓
Auth server verifies verifier matches original challenge
```

Even if someone intercepts the code, they cannot use it without the `code_verifier`.

#### 3. Client Credentials
Server to server, no user involved. Machine to machine authentication:

```
Your service → sends client_id + client_secret to auth server
        ↓
Auth server returns access token
        ↓
Your service calls another API with the token
```

#### 4. Device Authorization
For devices with no browser (Smart TVs, CLI tools):

```
Device shows: "Go to example.com/activate and enter: GHAZ-1234"
        ↓
User logs in on their phone/laptop
        ↓
Device polls auth server until approved
        ↓
Device receives token
```

#### 5. Implicit Flow
**Deprecated — do not use.** Replaced by PKCE.

### Which flow to use

| Situation | Flow |
|---|---|
| Web app with backend | Authorization Code |
| React / mobile app, no backend | Authorization Code + PKCE |
| Server to server | Client Credentials |
| Smart TV, CLI tool | Device Authorization |

## 16. OpenID Connect (OIDC)

### OAuth 2.0 vs OIDC

| | OAuth 2.0 | OIDC |
|---|---|---|
| Purpose | **Authorization** (what can this app access?) | **Authentication** (who is this user?) |
| Token issued | Access token + Refresh token | + ID token |
| ID token format | N/A | Always JWT |

OIDC is built **on top of** OAuth 2.0. It adds user identity to the OAuth framework.

### The three tokens in OIDC

| Token | Format | Purpose | Lifetime |
|---|---|---|---|
| Access token | JWT or Opaque | Authorize API calls | Short (15min–1hr) |
| ID token | Always JWT | Identify the user | Short |
| Refresh token | Opaque | Get new access tokens silently | Long (days/weeks) |

### Refresh token flow
Access tokens are intentionally short-lived. Refresh tokens silently renew them:

```
Access token expires → 401
        ↓
App sends refresh token to auth server
        ↓
Auth server returns new access token
        ↓
User never notices
```

Refresh tokens are opaque and stored server-side so they can be **revoked** — logging out or compromised accounts are handled by invalidating the refresh token.

### OIDC in OpenAPI
OIDC has a discovery endpoint — no need to spell out auth details in the spec:

```yaml
components:
  securitySchemes:
    openIdConnect:
      type: openIdConnect
      openIdConnectUrl: https://accounts.google.com/.well-known/openid-configuration
```

### Discovery endpoint
Every OIDC provider publishes a machine-readable document at `/.well-known/openid-configuration`:

```json
{
  "issuer": "https://accounts.google.com",
  "authorization_endpoint": "https://accounts.google.com/o/oauth2/auth",
  "token_endpoint": "https://oauth2.googleapis.com/token",
  "userinfo_endpoint": "https://openidconnect.googleapis.com/v1/userinfo",
  "jwks_uri": "https://www.googleapis.com/oauth2/v3/certs",
  "scopes_supported": ["openid", "email", "profile"],
  "grant_types_supported": ["authorization_code", "refresh_token"]
}
```

Tooling fetches this document and configures itself automatically. No manual hardcoding of endpoints.

In Spring Boot — one line of config is all you need:
```properties
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://accounts.google.com
```
Spring Security fetches the discovery document, finds the `jwks_uri`, fetches public keys, and starts verifying JWTs automatically.

## 17. JWKS & Asymmetric Keys

### The problem with HS256 in microservices

HS256 uses one secret key to both sign and verify. In a distributed system:

```
Auth Service    → signs tokens with secret key
Orders Service  → needs secret key to verify
Users Service   → needs secret key to verify
Payments Service → needs secret key to verify
```

Sharing the secret key across multiple services is a security risk — if any service is compromised, an attacker can forge tokens.

### RS256 solution — asymmetric key pair

RS256 uses two mathematically linked keys:
- **Private key** — only the Auth Service has this. Used to **sign** tokens.
- **Public key** — anyone can have this. Used to **verify** tokens only.

```
Auth Service signs with private key → token
Orders/Users/Payments verify with public key → valid
```

You **cannot sign with the public key** — only verify. Sharing it widely is completely safe.

### JWKS (JSON Web Key Set)
The standard format for publishing public keys so services can fetch them automatically.

Auth Service publishes its public key at:
```
https://auth.example.com/.well-known/jwks.json
```

The response:
```json
{
  "keys": [
    {
      "kty": "RSA",
      "kid": "key-id-1",
      "use": "sig",
      "n": "the public key material...",
      "e": "AQAB"
    }
  ]
}
```

Other services fetch this, get the public key, and verify incoming JWTs — without ever knowing the private key.

### The kid (Key ID) field
Both the JWKS document and the JWT header contain a `kid`. This tells the verifying service which specific public key to use — important because identity providers rotate keys periodically and can have multiple active keys at once.

JWT header with `kid`:
```json
{
  "alg": "RS256",
  "kid": "key-id-1"
}
```

### Full RS256 flow
```
1. User logs in → Auth Service
2. Auth Service signs JWT with private key
3. JWT returned to client
4. Client sends JWT to Orders Service
5. Orders Service fetches public key from jwks_uri
6. Orders Service verifies signature using public key
7. Valid → processes request
```

### Summary

```
HS256 (symmetric)
  One secret key → signs and verifies
  Good for: single server
  Bad for: microservices (secret must be shared)

RS256 (asymmetric)
  Private key → only auth server, only signs
  Public key  → anyone can have it, only verifies
  Good for: microservices (public key is safe to share)

JWKS
  Standard format for publishing public keys
  Services fetch from /.well-known/jwks.json automatically
  No manual key sharing needed
```
