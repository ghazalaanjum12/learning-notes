## 1. Maven & Dependencies

### Lombok in `pom.xml`
- Lombok must have an explicit `<version>` tag inside `<annotationProcessorPaths>` — it does **not** inherit the version from the `<dependencies>` block.
- Use version `1.18.36` (latest stable).

### MapStruct in `pom.xml`
- Version `1.6.3` is correct for MapStruct.
- Never declare two `maven-compiler-plugin` blocks — the second overrides the first. Merge them into one with both processors:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>
        <annotationProcessorPaths>
            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>1.18.36</version>
            </path>
            <path>
                <groupId>org.mapstruct</groupId>
                <artifactId>mapstruct-processor</artifactId>
                <version>1.6.3</version>
            </path>
        </annotationProcessorPaths>
    </configuration>
</plugin>
```

### jjwt Dependencies
jjwt is split into 3 modules (since 0.11.0). Use all three:

```xml
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>0.11.5</version>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-impl</artifactId>
    <version>0.11.5</version>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-jackson</artifactId>
    <version>0.11.5</version>
    <scope>runtime</scope>
</dependency>
```

- `jjwt-api` — public API you use in code (compile scope)
- `jjwt-impl` — actual implementation (runtime only)
- `jjwt-jackson` — JSON serialization (runtime only)

## 2. MapStruct

### How MapStruct works
MapStruct generates implementation code at compile time by scanning your mapper interface and matching method signatures.

### Type-based method selection
When MapStruct needs to convert `String` → `JsonNullable<String>`, it scans all methods in the mapper and finds one that matches the input/output types automatically. No annotation needed.

```java
@Mapper(componentModel = "spring")
public interface UserMapper {

    @Mapping(target = "image", source = "imageUrl")
    @Mapping(target = "bio", source = "bio")
    com.conduit.openapi.model.User toUserDTO(User user);

    // MapStruct auto-picks this up for any String → JsonNullable<String> conversion
    default <T> JsonNullable<T> toJsonNullable(T value) {
        return JsonNullable.of(value);
    }
}
```

### Generic method syntax explained
```
default  <T>           JsonNullable<T>    toJsonNullable(T value)
↑         ↑                 ↑                    ↑
modifier  declaring T   return type         parameter type
```
The `<T>` between `default` and the return type declares that this is a generic method. Without it, Java wouldn't know what `T` is.

### Best practice for response wrapping
Mappers should handle field-to-field conversion only. Wrapping (e.g. `UserResponse.setUser(...)`) is assembly, not mapping — do it inline in the controller:

```java
UserResponse userResponse = new UserResponse();
userResponse.setUser(userMapper.toUserDTO(user));
return ResponseEntity.status(HttpStatus.CREATED).body(userResponse);
```

## 3. Authentication Concepts

### Token-based auth vs OAuth

| | Token Auth | OAuth Client Credentials |
|---|---|---|
| Who authenticates? | A human user | A machine/service |
| Who issues the token? | Your own app | A dedicated auth server |
| Third party involved? | No | Yes |
| Use case | User logs into your app | Service A calls Service B |

- **Token-based auth** — user logs in, your app issues a JWT, user sends it with every request.
- **OAuth** — a protocol for delegated authorization. Client Credentials flow is machine-to-machine with no user involved.
- They look similar because both end up with a bearer token in a header, but the flow and intent are different.

### OpenAPI security scheme
JWT doesn't have its own type in OpenAPI spec, so it's declared as `apiKey`. This is a spec limitation, not a design choice — the token inside is still a JWT.

## 4. Spring Security

### Why implement `UserDetails`?
Spring Security doesn't know your `User` entity — it doesn't know if your password field is called `password` or `hashedPassword`, or whether you use email or username. `UserDetails` is a contract (interface) that bridges your entity to Spring Security.

```java
@Entity
public class User implements UserDetails {

    private String email;
    private String password;

    @Override
    public String getUsername() {
        return email; // tell Spring Security to use email as username
    }

    @Override
    public String getPassword() {
        return password;
    }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of(); // no roles for now
    }

    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return true; }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return true; }
}
```

### Password hashing
Spring Security expects hashed passwords. It never stores or compares plain text.

```
Registration:  plainText → BCrypt hash → save to DB
Login:         plainText → BCrypt hash → compare with DB hash
```

Register `BCryptPasswordEncoder` as a bean:

```java
@Bean
public PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}
```

## 5. JPA Timestamps

### Prefer JPA over Hibernate-specific annotations
`@CreationTimestamp` and `@UpdateTimestamp` are Hibernate-specific. Prefer standard JPA using a shared base class:

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false, name = "created_at")
    private Instant createdAt;

    @LastModifiedDate
    @Column(name = "updated_at")
    private Instant updatedAt;
}
```

Enable auditing in config:
```java
@Configuration
@EnableJpaAuditing
public class JpaConfig {
}
```

All entities just extend `BaseEntity` — no need to repeat timestamp fields.

## 6. JWT Service

### Secret key requirements
The secret key must be at least 256 bits (32 bytes) for HS256. Store it as a Base64 encoded string in `application.properties`.

Generate one using Git Bash:
```bash
openssl rand -base64 32
```

```properties
security.jwt.secret-key=Z0T4My41pvlKdselrdZakXs5ka/vXeJVrJhPYGldFiA=
security.jwt.expiration-time=86400000
```

`86400000` milliseconds = 24 hours.

### Secret key journey
```
Base64 string (application.properties)
    → Decoders.BASE64.decode()  → raw bytes
    → Keys.hmacShaKeyFor()      → SecretKey object used to sign/verify
```

`Keys.hmacShaKeyFor` also validates the key is long enough for HS256 and throws if not.

### Token generation
```java
Jwts.builder()
    .setClaims(extraClaims)
    .setSubject(userDetails.getUsername())
    .setIssuedAt(new Date(...))
    .setExpiration(new Date(...))
    .signWith(getSignInKey(), SignatureAlgorithm.HS256)
    .compact();
```

### Signature verification
Signature is verified implicitly inside `parseClaimsJws(token)` — NOT explicitly in `isTokenValid`. If someone tampers with the token, `parseClaimsJws` throws a `SignatureException` before any other checks run.

```
isTokenValid()
    → extractUsername()
        → extractClaim()
            → extractAllClaims()
                → parseClaimsJws() ← signature verified HERE
    → check username matches
    → check not expired
```

### Overall JWT flow
```
Registration/Login → generateToken(user) → send JWT to client
                                                    ↓
Next request → client sends JWT in header
             → extractUsername from token
             → load user from DB
             → isTokenValid(token, user)
             → allow or reject
```

### Why write JwtService manually?
Spring Security handles authentication mechanics but stays unopinionated about token format. It doesn't decide:
- JWT vs opaque tokens
- What claims to include
- Signing algorithm (HS256, RS256, etc.)
- Token expiration

This flexibility is intentional. Spring does ship `spring-boot-starter-oauth2-resource-server` for built-in JWT support, but it's geared towards OAuth2 flows and more complex to set up.

## 7. OpenSSL vs OpenSSH

| | OpenSSL | OpenSSH |
|---|---|---|
| Purpose | Cryptography toolbox | Remote server access |
| Used for | Generating keys, certificates, hashing | `ssh user@server`, GitHub SSH keys |
| Your use case | `openssl rand -base64 32` | Not relevant here |
