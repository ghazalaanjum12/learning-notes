# Spring Boot Learning Notes: Exceptions & Validation

## 1. Custom Exceptions

### Checked vs Unchecked
- **Checked** (extends `Exception`): compiler forces every caller up the stack to `catch` or declare `throws`. Painful with generated code (e.g. OpenAPI interfaces) since you can't edit their signatures.
- **Unchecked** (extends `RuntimeException`): propagates automatically with zero ceremony — no `throws` needed anywhere in the chain. This is why `DuplicateIdException` extends `RuntimeException`: it needs to bubble from `RegistrationService` → generated delegate → generated controller → `GlobalExceptionHandler` without touching any of the generated code in between.

```java
public class DuplicateIdException extends RuntimeException {
    public DuplicateIdException(String message) {
        super(message); // stores the message in Throwable's detailMessage field
    }
}
```
- `super(message)` matters: without it, `getMessage()` returns `null` even if you pass a string when throwing.
- Rule of thumb: unchecked = business-rule violations / "let a central handler decide" (validation failures, not-found, duplicates). Checked = conditions the immediate caller is expected to recover from right there.

### Where custom exceptions live
- Small project: keep `GlobalExceptionHandler` and custom exceptions (`DuplicateIdException`, etc.) together in one `exception` package. Splitting into `exception.custom` / `exception.handler` is a pattern that earns its keep at ~8+ files, not before.

## 2. Duplicate-Entry Handling Pattern

Two layers of defense in `RegistrationService`, not split across delegate + service:

```java
public UserResult registerUser(User user) {
    if (userRepository.existsByEmail(user.getEmail())) {          // fast path
        throw new DuplicateIdException("Email already registered: " + user.getEmail());
    }
    try {
        User saved = userRepository.save(user);                   // safety net for race conditions
        ...
    } catch (DataIntegrityViolationException e) {                 // Spring's translated SQL exception
        throw new DuplicateIdException("Email already registered: " + user.getEmail());
    }
}
```
- **Why both:** the existence check can race under concurrent requests (TOCTOU) — two threads can both pass the check before either commits. The DB unique constraint + catch is what actually guarantees correctness; the check is just a nicer/faster UX path.
- **Why not in the delegate:** delegates should stay thin translators (request → service → response). Business rules like "is this a duplicate" belong in the service so they apply no matter what calls `registerUser()` (API, batch import, tests, etc.).
- Spring auto-translates `java.sql.SQLIntegrityConstraintViolationException` → `DataIntegrityViolationException` (unchecked, `org.springframework.dao`) — catch the translated one, not the raw JDBC one.

## 3. Constructor Injection vs Field Injection

**Avoid:**
```java
@Autowired
private RegistrationService registrationService;
```

**Prefer:**
```java
@RequiredArgsConstructor   // Lombok generates the constructor
public class UsersApiDelegateImpl implements UsersApiDelegate {
    private final RegistrationService registrationService;
}
```

Why constructor injection wins:
1. `final` fields → immutable, can't be silently reassigned.
2. Testable without a Spring context — can `new` the class directly with mocks, no reflection needed.
3. A bloated constructor signature visibly signals "this class does too much"; hidden `@Autowired` fields don't.
4. Recommended by Spring team since Spring 4.3 (2016). Since 4.3, `@Autowired` is optional if there's exactly one constructor — Spring uses it automatically.

## 4. Bean Validation (Jakarta) — The Full Picture

### Spec vs Implementation
- `jakarta.validation.constraints.*` (`@NotNull`, `@NotBlank`, etc.) is just a **specification** — annotations with no behavior on their own.
- **Hibernate Validator** is the reference **implementation** that actually reads the annotations via reflection and evaluates them. (Unrelated to Hibernate ORM despite the shared name/parent project.)
- Without an implementation on the classpath, `@Valid` is a **silent no-op** — no error, no exception, request just sails through. Symptom: user gets created in DB with `null`/blank fields and no validation error anywhere.

### The fix
```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
```
Tell-tale log line when it's missing (only logged at INFO, easy to miss):
```
Failed to set up a Bean Validation provider: jakarta.validation.NoProviderFoundException...
```

### Cascading into nested objects
`@Valid` does **not** automatically recurse into nested objects — the parent field needs `@Valid` too:
```java
@NotNull @Valid
public NewUser getUser() { ... }   // @Valid here cascades validation into NewUser
```
And the entry point (generated `UsersApi` interface) needs `@Valid` on the `@RequestBody` param — OpenAPI codegen usually adds this automatically.

### `@NotNull` vs `@NotBlank`
- `@NotNull` only rejects literal `null` — an empty string `""` or whitespace `"   "` passes right through.
- `@NotBlank` rejects null, empty, and whitespace-only strings — what you actually want for required text fields like `username`.
- **Real bug hit in this project:** `@NotNull` on `username` let `""` through; user was created with a blank username. Log tell-tale: `Read "application/json..." to [class CreateUserRequest { user: class NewUser { username: ...` (nothing after the colon = empty string, not null).

### Fixing it without touching the OpenAPI spec
Since generated files (`NewUser.java`) get overwritten on regen, don't hand-edit them. Options, in order of idiomatic-ness:
1. **Spec-level fix** (best if you own the spec): add `minLength: 1` in the OpenAPI YAML → codegen emits `@NotBlank`/`@Size`. Not always desirable (spec churn, shared spec).
2. **Manual check in the service** (simplest): `StringUtils.hasText(user.getUsername())`, throw a custom exception. Fine for one-off business rules, but doesn't flow through the standard validation-exception pipeline and isn't visible in API docs.
3. **Custom `Validator` + `@InitBinder`** (chosen approach — see below): keeps everything in the standard `@Valid` pipeline without touching generated code or the spec.

## 5. Custom Validators via `@InitBinder`

### The `Validator`
```java
// com.conduit.validation.NewUserValidator.java
@Component
public class NewUserValidator implements Validator {
    @Override
    public boolean supports(Class<?> clazz) {
        return NewUser.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        NewUser newUser = (NewUser) target;
        if (!StringUtils.hasText(newUser.getUsername())) {
            errors.rejectValue("username", "field.required", "must not be blank");
        }
    }
}
```
- `rejectValue(field, code, message)` → **field-level** error (use this for single-field checks).
- `reject(code, message)` → **global** error, not tied to a field (use for cross-field rules like "start date before end date"). Retrieved differently in the handler (`getGlobalErrors()` vs `getFieldErrors()`).
- Use `org.springframework.util.StringUtils.hasText()`, not Apache Commons `StringUtils.isBlank()` — avoids an extra dependency when you're already all-in on Spring.

### Wiring: why `@InitBinder` on the delegate doesn't work
`@InitBinder` only works on classes Spring MVC recognizes as controller-layer beans (`@Controller`/`@RestController`/`@ControllerAdvice`). In the OpenAPI-delegate pattern, the actual `@RestController` is the **generated** `UsersApiController`, not `UsersApiDelegateImpl` (a plain `@Service`) — so `@InitBinder` on the delegate is silently never invoked.

### The fix: global `@ControllerAdvice`
```java
// com.conduit.configuration.GlobalBinderConfig.java
@RestControllerAdvice
public class GlobalBinderConfig {
    private final NewUserValidator newUserValidator;

    public GlobalBinderConfig(NewUserValidator newUserValidator) {
        this.newUserValidator = newUserValidator;
    }

    @InitBinder
    public void initBinder(WebDataBinder binder) {
        binder.addValidators(newUserValidator);
    }
}
```
- This is the same mechanism family as `@ExceptionHandler` on `GlobalExceptionHandler` — both are `@ControllerAdvice`-style cross-cutting hooks, standard and documented, not a workaround.
- Applies globally to all controllers, which is required here since you can't put `@InitBinder` directly on the generated controller. Scope individual validators narrowly via `supports()` so they don't interfere with unrelated endpoints as the app grows.
- Result: custom validator errors and annotation-based errors (`@NotBlank`, etc.) both surface through the same `MethodArgumentNotValidException` → one `GlobalExceptionHandler` method covers both.

### The handler
```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
    List<String> fieldMessages = ex.getBindingResult().getFieldErrors().stream()
        .map(fe -> fe.getField() + ": " + fe.getDefaultMessage())
        .toList();

    List<String> globalMessages = ex.getBindingResult().getGlobalErrors().stream()
        .map(ObjectError::getDefaultMessage)
        .toList();

    List<String> allMessages = Stream.concat(fieldMessages.stream(), globalMessages.stream()).toList();
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(new ErrorResponse(allMessages));
}
```

## 6. Folder Structure Conventions Landed On

```
com.conduit
├── configuration
│   ├── SecurityConfig.java
│   ├── JwtAuthenticationFilter.java
│   └── GlobalBinderConfig.java      # @ControllerAdvice wiring custom validators globally
├── validation
│   ├── UpdateUserValidator.java
│   └── NewUserValidator.java        # individual Validator implementations
└── exception
    ├── GlobalExceptionHandler.java
    └── DuplicateIdException.java    # handler + custom exceptions together (small project)
```
Rule of thumb: group by **role** (config wiring vs validators vs error-handling), not by feature, while the project is small enough that each package stays under ~8 files.

## 7. Debugging Technique Worth Remembering
When a validation-looking bug shows up, check the raw request-binding DEBUG log line:
```
Read "application/json;charset=UTF-8" to [class CreateUserRequest { user: class NewUser { username: ...
```
What appears (or doesn't) right after the field name tells you `null` vs `""` vs a real value — this is what pinpointed the `@NotNull`-lets-blank-through bug directly, before touching any code.
