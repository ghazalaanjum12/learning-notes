# Authentication Notes

## 1. HTTP Authentication Headers

Two key headers at the protocol level:

**`WWW-Authenticate`** — sent by the **server** on a `401` to tell the client what it expects:
```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
```

**`Authorization`** — sent by the **client** with credentials:
```
GET /users
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

> The scheme identifier (`Basic`, `Bearer`) tells the server how to interpret the credentials.
> That is literally all HTTP authentication is at the protocol level — everything else (JWT, OAuth, OIDC) is implementation detail on top.

### When does `WWW-Authenticate` actually appear?
Only when a request **fails with a 401**:
- Client hits a protected route **without** a token
- Client sends an **expired or invalid** token

In a well-behaved JWT flow you mostly never see it — the client is always sending the token correctly.

```
WWW-Authenticate = server's error message explaining the rules
Authorization    = client already following the rules
```

## 2. The Authentication Scheme

The scheme is the **first word** — a label that tells the server what type of credential is being sent and how to read it:

```
Authorization: Bearer eyJhbG...
               ↑       ↑
             scheme   actual credential
```

### Two most common schemes:

**`Basic`** — credential is base64-encoded `username:password`
```
Authorization: Basic dXNlcjpwYXNzd29yZA==
                     ↑
                     base64("user:password")
```

**`Bearer`** — credential is a token (JWT or opaque)
```
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
                      ↑
                      token string
```

## 3. Main Authentication Types

### 3.1 Basic Auth
- Send username + password on **every request** (base64 encoded)
- Part of the HTTP auth scheme
- No tokens, no sessions
- Simple but credentials travel every request
- Used for internal tools, simple APIs

### 3.2 Session-Based Auth
- **NOT** part of the HTTP auth scheme — uses cookies instead
- Stateful — requires DB lookup on every request

**Flow:**
```
1. User submits login form (not an Authorization header)
2. Server verifies credentials against DB
3. Server creates session, stores in DB:
   sessions table: { id: "abc123", userId: 42, expiresAt: ... }
4. Server responds with:
   Set-Cookie: sessionId=abc123       ← not WWW-Authenticate
5. Browser auto-attaches on every request:
   Cookie: sessionId=abc123           ← not Authorization
6. Server hits DB → SELECT * FROM sessions WHERE id = 'abc123'
7. Request proceeds
```

> The DB lookup on every single request is the bottleneck.

### 3.3 Token-Based Auth (Bearer scheme)

Two types of tokens used in the `Bearer` scheme:

| | JWT | Opaque Token |
|---|---|---|
| Looks like | `eyJhbG...` (encoded data) | `a3f8c2d9e1b...` (random string) |
| Contains info? | Yes — payload inside | No — means nothing on its own |
| Validation | Verify signature (no DB) | Must hit DB to look up |
| Who knows the user? | Anyone with the secret key | Only the server |

```
Bearer scheme
├── JWT        → self-contained, no DB needed
└── Opaque     → random string, needs DB lookup
```

> `Bearer` just means "here's a token" — it says nothing about what the token actually is.

#### JWT Flow:
```
1.  POST /users/login with username + password
2.  Server validates credentials against DB
3.  Server creates payload: { sub: "ghazala", role: "admin", exp: ... }
4.  Server signs with secret key → JWT
5.  JWT returned to client
6.  Client stores JWT
7.  Every subsequent request: Authorization: Bearer <JWT>
8.  Server verifies signature — no DB needed
9.  Server reads payload to know who the user is
```

#### Why JWT eliminates the DB lookup:
The token itself **contains** the user info and is **cryptographically signed**. The server just:
1. Checks the signature is valid (pure math, no DB)
2. Reads the data directly out of the token

#### Opaque Token Flow:
```
Login  → server generates random string "a3f8c2d9e1b"
       → stores in DB: { token: "a3f8c2d9e1b", userId: 42 }
       → gives to client

Request → Authorization: Bearer a3f8c2d9e1b
        → server hits DB to look up who this belongs to
```

### 3.4 OAuth 2.0
- Not really authentication — it's **delegated authorization**
- Answers: *"Can this app access my data on another service?"*
- Produces tokens (usually Bearer tokens under the hood)
- e.g. *"Allow this app to access my Google Drive"*

### 3.5 OpenID Connect (OIDC)
- OAuth 2.0 **+ identity layer** on top
- OAuth alone doesn't tell you *who* the user is — OIDC adds that
- What *"Login with Google"* actually uses under the hood

#### OIDC Flow:
```
1.  User clicks "Login with Google" on your app

2.  Your app redirects user to Google's authorization endpoint:
    https://accounts.google.com/auth?
      client_id=your_app_id
      redirect_uri=https://yourapp.com/callback
      scope=openid email profile       ← "openid" makes this OIDC not just OAuth
      response_type=code

3.  Google shows login page — user enters credentials

4.  Google asks "Allow YourApp to access your profile?" → user clicks Allow

5.  Google redirects back to your app with a one-time code:
    https://yourapp.com/callback?code=AUTH_CODE_XYZ

6.  Your app sends that code to Google's token endpoint
    (server to server — user doesn't see this)
    POST https://accounts.google.com/token
    { code: AUTH_CODE_XYZ, client_secret: ... }

7.  Google responds with THREE things:
    {
      access_token:  "ya29.xxx"      ← OAuth part  (access Google APIs)
      refresh_token: "1//xxx"        ← get new access tokens later
      id_token:      "eyJhbG..."     ← OIDC part   (who the user is)
    }

8.  Your app decodes the id_token (it's a JWT):
    {
      sub:   "1234567890",           ← unique user id at Google
      email: "user@gmail.com",
      name:  "John Doe",
      exp:   ...
    }

9.  Now your app knows who the user is — create a session or
    issue your own JWT from here
```

> **Key distinction:**
> - `access_token` → "act on behalf of user" (OAuth)
> - `id_token` → "here's who the user is" (OIDC)
>
> Without the `openid` scope, you only get an `access_token` — you can access Google APIs but have no idea who the user actually is.

## 4. Comparison Summary

### Session vs JWT

| | Session | JWT |
|---|---|---|
| Storage | Server DB | Client (the token itself) |
| Validation | DB lookup every request | Signature check (no DB) |
| Scalability | Harder (DB is a bottleneck) | Easier (stateless) |
| Revocation | Easy (delete the row) | Hard (token valid until expiry) |

### All Types at a Glance

| Type | Mechanism | Stateful? | Part of HTTP Auth Scheme? |
|---|---|---|---|
| Basic Auth | Password every request | No | Yes |
| Session Auth | Cookie + DB | Yes | No (uses cookies) |
| JWT (Bearer) | Self-contained token | No | Yes |
| Opaque (Bearer) | Random token + DB | Yes | Yes |
| OAuth 2.0 | Delegated authorization | — | Produces Bearer tokens |
| OIDC | OAuth 2.0 + identity | — | Produces Bearer tokens |

### The One-Line Summary of Each

```
Basic    → who are you? (password every time)
Session  → who are you? (cookie + DB)
JWT      → who are you? (self-contained token)
Opaque   → who are you? (random token + DB)
OAuth    → can this app access your stuff?
OIDC     → OAuth + who are you?
```

> OAuth and OIDC are at a **different level** — they are about **cross-service trust**, not just logging into your own app.

## 5. Maven Wrapper (Bonus)

| File/Folder | Purpose |
|---|---|
| `.mvn/` | Contains wrapper config — specifies which Maven version to download |
| `mvnw` | Shell script for Mac/Linux to run Maven via the wrapper |
| `mvnw.cmd` | Same but for Windows |

**Always commit these files.** Their purpose is to ensure everyone on the team uses the same Maven version without needing Maven installed globally.

```
# Instead of this (uses whatever Maven is globally installed)
mvn spring-boot:run

# Do this (uses the project-pinned version)
./mvnw spring-boot:run        # Mac/Linux
mvnw.cmd spring-boot:run      # Windows
```

The key file is `.mvn/wrapper/maven-wrapper.properties`:
```properties
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.6/apache-maven-3.9.6-bin.zip
```

> Same philosophy as `package-lock.json` in Node or `Pipfile.lock` in Python — **pin your tooling at the project level, not the machine level.**
