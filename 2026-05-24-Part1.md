## Validation

### Custom Constraint Annotation (Bean Validation / JSR-380)

The standard modern approach for validating a POJO is a custom annotation backed by a `ConstraintValidator`. This is the **industry standard** when you own the POJO.

**1. Define the annotation:**
```java
// validation/AtLeastOneField.java
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = AtLeastOneFieldValidator.class)
public @interface AtLeastOneField {
    String message() default "At least one field must be provided";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

**2. Implement the validator:**
```java
// validation/AtLeastOneFieldValidator.java
public class AtLeastOneFieldValidator implements ConstraintValidator<AtLeastOneField, Object> {

    @Override
    public boolean isValid(Object obj, ConstraintValidatorContext context) {
        if (obj == null) return false;
        return Arrays.stream(obj.getClass().getDeclaredFields())
                .peek(f -> f.setAccessible(true))
                .map(f -> {
                    try { return f.get(obj); } catch (IllegalAccessException e) { return null; }
                })
                .anyMatch(Objects::nonNull);
    }
}
```

**3. Annotate the POJO:**
```java
@AtLeastOneField
public class UpdateUser {
    private String username;
    private String email;
    private String bio;
}
```

**4. Trigger validation in the controller:**
```java
public ResponseEntity<UserResponse> updateCurrentUser(@Valid UpdateCurrentUserRequest body) {
    // @Valid triggers validation automatically before this point
}
```

> The reflection-based validator works generically on any POJO — adding new fields to `UpdateUser` later requires no changes to the validator.

### When NOT to use a POJO annotation validator
If your POJO is **generated by OpenAPI**, you cannot annotate it directly. Instead validate manually in the delegate or service.

### Manual null check in delegate (simplest approach)
```java
if (user.getUsername() == null && user.getEmail() == null && user.getBio() == null) {
    return ResponseEntity.status(HttpStatus.BAD_REQUEST).build();
}
```

### Spring `Validator` interface (older, less common now)
```java
@Component
public class UpdateUserValidator implements Validator {

    @Override
    public boolean supports(Class<?> clazz) {
        return UpdateUser.class.equals(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        UpdateUser user = (UpdateUser) target;
        if (user.getUsername() == null && user.getEmail() == null) {
            errors.reject("atLeastOneField", "At least one field must be provided");
        }
    }
}
```
- `reject` → error on the **whole object**
- `rejectValue("fieldName", ...)` → error on a **specific field**
- `BeanPropertyBindingResult` is the container that holds errors; the name argument is just a prefix for error codes (e.g. for i18n message property files)
- This approach is **old** — modern apps use Bean Validation annotations (`@NotNull`, `@NotBlank`) directly on POJOs instead

## HTTP Status Codes

| Code | Meaning | When to use |
|------|---------|-------------|
| 400  | Bad Request | Client sent invalid/missing data |
| 422  | Unprocessable Entity | Request well-formed but semantically wrong (e.g. start date > end date) |
| 200  | OK | Successful GET/PUT |
| 201  | Created | Successful POST |

For a missing fields scenario, **400 is the safer, more widely understood choice**.

## JsonNullable

Used when you need to distinguish between three states for a field:

| State | Meaning |
|-------|---------|
| `undefined` | Client didn't send the field — don't change it |
| `null` | Client explicitly sent null — clear the value |
| `value` | Client sent a value — update it |

### Checking in a validator
```java
// For nullable String fields — simple null check
if (user.getUsername() == null) { ... }

// For JsonNullable fields — use isDefined()
if (!user.getBio().isDefined()) { ... }  // true for both null and a value
```

### Updating entity fields
```java
if (updateUser.getUsername() != null) user.setUsername(updateUser.getUsername());
if (updateUser.getEmail() != null) user.setEmail(updateUser.getEmail());
if (updateUser.getBio().isDefined()) user.setBio(updateUser.getBio().get()); // .get() can return null or a value
```

### Jackson setup for JsonNullable
Requires `jackson-databind-nullable` dependency and registering the module:
```java
@Configuration
public class JacksonConfig {
    @Bean
    public JsonNullableModule jsonNullableModule() {
        return new JsonNullableModule();
    }
}
```
> **Note:** `jackson-databind-nullable` only supports **Jackson 2.x**. It does NOT support Jackson 3.x (used in Spring Boot 4.x) as of 2025.

## Spring Security — DaoAuthenticationProvider

The correct way to configure it (no-arg constructor, both set via setters):
```java
@Bean
public AuthenticationProvider authenticationProvider() {
    DaoAuthenticationProvider authProvider = new DaoAuthenticationProvider();
    authProvider.setUserDetailsService(userDetailsService);
    authProvider.setPasswordEncoder(passwordEncoder);
    return authProvider;
}
```

## Jackson & ObjectMapper

- **ObjectMapper** is Jackson's core class — converts between JSON and Java objects
- **Jackson2ObjectMapperBuilderCustomizer** is a hook to customize Spring Boot's auto-configured ObjectMapper without replacing it entirely
- Spring Boot automatically picks up any `Module` beans (like `JsonNullableModule`) and registers them

## Database Driver

A driver is a translator between your Java app and your database. Without it, Spring Boot doesn't know how to talk to your specific database.

```
Your Java App → JDBC API → Driver → Database
```

Example for MySQL in `pom.xml`:
```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

And in `application.properties`:
```properties
spring.datasource.url=jdbc:mysql://localhost:3306/mydb
spring.datasource.username=root
spring.datasource.password=password
```

## i18n (Internationalization)

**i18n** = internationalization (18 letters between i and n). Making your app support multiple languages.

Spring resolves error messages from property files based on the user's locale (`Accept-Language` header):
```
# messages.properties (default)
updateUser.atLeastOneField=At least one field must be provided

# messages_fr.properties
updateUser.atLeastOneField=Au moins un champ doit être fourni
```
The prefix (e.g. `updateUser`) in `BeanPropertyBindingResult` is used as the key prefix when looking up these files.

## Common Gotchas

- **Duplicate bean error (`BeanDefinitionOverrideException`)** — usually caused by two conflicting versions of an autoconfigure jar on the classpath. Check with `mvn dependency:tree | findstr <keyword>` (Windows) or `| grep` (Mac/Linux).
- **`spring-boot-autoconfigure` manually added** — don't add it manually; it comes transitively. Adding it explicitly can cause version conflicts.
- **Springdoc 3.x on Spring Boot 3.x** — springdoc 3.x pulls in `spring-boot-webmvc 4.x` which conflicts with Spring Boot 3.x autoconfigure.
