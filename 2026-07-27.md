# Spring Boot / JPA Revision Notes — Conduit Project

## 1. PATCH Semantics: Omitted vs Null vs Empty

**The problem:** A plain `String email` field can't distinguish:
- Field omitted from JSON → `null`
- Field explicitly sent as `"email": null` → also `null`

**Option A — `JsonNullable<T>` (requires OpenAPI spec change: `nullable: true`)**
```java
if (field.isPresent() && StringUtils.isBlank(field.get())) {
    errors.rejectValue(fieldName, "field.required", "can't be blank");
}
```
Three states: not present / present+null / present+value.

**Option B — Presence map (`Map<String,Object>` or `JsonNode`), no spec change needed**
Bind raw body, check `.containsKey(field)` before validating. More correct, more machinery.

**Option C — Pragmatic collapse (what we used for Conduit)**
Treat "omitted" and "explicit null" as the same no-op signal. Only reject **explicit empty string**:
```java
private void rejectIfEmpty(String value, String fieldName, Errors errors) {
    if (value != null && value.isBlank()) {
        errors.rejectValue(fieldName, "field.required", "can't be blank");
    }
}
```
Update logic: `if (value != null) existingUser.setX(value);`

Only reach for A/B when a field needs a genuine "clear this" action (e.g. `bio`, `image`). For required-ish fields like `email`/`username`/`password`, C is enough — nobody legitimately wants to null those via PATCH.

**RFC 7396 (JSON Merge Patch)** is the actual industry standard for this problem when you need it broadly across many PATCH endpoints — via `jakarta.json.JsonMergePatch`. Overkill for a single endpoint on a learning project.

## 2. Validator Gotchas

- `errors.rejectValue(field, code, msg)` → field-specific error (`FieldError`)
- `errors.reject(code, msg)` → object-level error (`GlobalError`), use when no single field is at fault (e.g. "at least one field must be provided" for an empty update payload)

```java
if (allFieldsNull) {
    errors.reject("field.required", "At least one field must be provided");
}
```

## 3. Stream/Optional Gotcha: Flattening Field Errors

```java
// WRONG — Optional<List<FieldError>>.stream() gives Stream<List<FieldError>>,
// so toMap's key mapper receives a List, not a FieldError
Optional.ofNullable(errors.getFieldErrors())
    .stream()
    .collect(Collectors.toMap(FieldError::getField, fe -> List.of(fe.getDefaultMessage())));

// RIGHT — flatMap to unwrap into individual FieldErrors
Optional.ofNullable(errors.getFieldErrors())
    .stream()
    .flatMap(List::stream)
    .collect(Collectors.toMap(
        FieldError::getField,
        fe -> List.of(fe.getDefaultMessage()),
        (existing, incoming) -> Stream.concat(existing.stream(), incoming.stream()).toList() // merge fn for duplicate keys
    ));
```
Note: `errors.getFieldErrors()` never actually returns `null` in Spring — `Optional.ofNullable` is defensive but not strictly required.

## 4. DTO vs Entity — Keep Them Separate

- **OpenAPI-generated model** (e.g. `UpdateUser`) = wire contract. Represents the API shape.
- **`@Entity`** = persistence contract. Represents the DB schema — relationships, cascades, fetch strategy, fields you'd never expose (password hash, audit columns).

No tool safely generates one from the other — they intentionally diverge. Convert between them with **MapStruct**:
```java
@Mapper(componentModel = "spring")
public interface UserMapper {
    void updateEntityFromDto(UpdateUser dto, @MappingTarget User entity);
}
```

## 5. `ddl-auto` Options

| Value | Behavior |
|---|---|
| `none` | No DDL. You manage schema (e.g. via migrations). |
| `validate` | Checks entities match schema, throws if mismatched. Creates nothing. |
| `update` | Creates/patches tables to match entities. Never drops columns. Doesn't reliably enforce new constraints on existing data. |
| `create` | Drops + recreates schema on every startup. |
| `create-drop` | Same as `create`, also drops on shutdown. Common for test DBs. |

- `update` = fine for early-stage dev (current Conduit setup).
- Production standard: `none`/`validate` + **Flyway** or **Liquibase** for versioned SQL migrations.

## 6. Owning Side vs Inverse Side

Bidirectional relationships share **one** foreign key column in the DB — only one side controls it.

```java
// OWNING SIDE — has @JoinColumn, holds the actual FK
@Entity
class Comment {
    @ManyToOne
    @JoinColumn(name = "article_id", nullable = false)
    private Article article;
}

// INVERSE SIDE — mappedBy, no FK, just reflects the owning side
@Entity
class Article {
    @OneToMany(mappedBy = "article", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Comment> comments = new ArrayList<>();
}
```

**Rule of thumb:** `@ManyToOne` is (almost) always the owning side.

**Trap:** setting only the inverse side (`article.getComments().add(comment)`) persists nothing. Must set the owning side too, or use a sync helper:
```java
public void addComment(Comment comment) {
    comments.add(comment);
    comment.setArticle(this);
}
```

## 7. Cascade Types

Controls whether parent operations (save/delete/update) automatically apply to children.

| Type | Effect |
|---|---|
| `PERSIST` | Saving parent also saves new children |
| `MERGE` | Updating parent also updates children |
| `REMOVE` | Deleting parent also deletes children |
| `ALL` | All of the above |
| `orphanRemoval = true` | Removing a child *from the collection* deletes it from DB (separate flag, not a CascadeType) |

**Use for:** genuine composition — child has no meaning without parent (`Article` → `Comment`).
**Don't use for:** plain associations — e.g. `Article` → `User` (author). Never want deleting a user to cascade-delete their articles.

## 8. Fetch Strategies

| Type | Default for | Behavior |
|---|---|---|
| `LAZY` | `@OneToMany`, `@ManyToMany` | Loaded only when getter is called |
| `EAGER` | `@ManyToOne`, `@OneToOne` | Loaded immediately with parent |

**Gotcha:** `@ManyToOne`/`@OneToOne` default to EAGER — commonly overridden to LAZY explicitly, since EAGER defaults can cascade-load large object graphs unintentionally.

**Gotcha:** accessing a LAZY field after the transaction/session has closed → `LazyInitializationException` (the most common JPA runtime error for beginners). Fix: map entity → DTO *inside* the transactional service method, before the session closes.

**Conduit default:** `LAZY` everywhere, use `JOIN FETCH` or DTO projections when you actually need related data.

## 9. `JOIN FETCH`

JPQL clause that loads a related entity **in the same query**, overriding laziness for one specific query (rather than flipping the whole relationship to EAGER globally).

**Problem it solves — N+1 queries:**
```java
List<Comment> comments = commentRepository.findByArticleId(articleId); // 1 query
comments.forEach(c -> c.getArticle().getTitle()); // N extra queries, one per comment
```

**Fix:**
```java
@Query("SELECT c FROM Comment c JOIN FETCH c.article WHERE c.article.id = :articleId")
List<Comment> findByArticleIdWithArticle(@Param("articleId") Long articleId);
```

**Regular `JOIN` vs `JOIN FETCH`:**
- `JOIN` — filters only, association stays lazy afterward
- `JOIN FETCH` — filters AND populates the association, no extra query later

**Watch out for:**
- `JOIN FETCH` on a `@OneToMany` collection can produce duplicate parent rows in raw SQL (Hibernate dedupes the Java objects automatically when returning entities, not DTO projections).
- Fetch-joining **two** collections at once → `MultipleBagFetchException`. Deeper topic, not usually needed for Conduit's scope.

---

## Quick Reference: Conduit Defaults Used

- `ddl-auto: update` for now → migrate to Flyway before calling it "production-style"
- Validators: pragmatic null-collapse (Option C above), not full `JsonNullable`
- All relationships: `LAZY` by default, `JOIN FETCH` when needed
- Cascade `ALL` + `orphanRemoval` only on true compositions (Article→Comment), never on Article→User
