# Spring Boot, Networking & Concurrency — Revision Notes

---

## 1. Ports

- A **port** is just a number (0–65535) assigned by the OS
- It acts as a label so the OS knows which application incoming data belongs to
- When Spring Boot starts, it registers port **8080** with the OS
- Port is **not** a connection — it's just an address
- Well known defaults: **HTTP → 80**, **HTTPS → 443** (which is why URLs don't show them)

---

## 2. Sockets

- A **socket** is a live object in memory representing an active connection
- It holds state: who connected, buffered data, etc.
- A socket is identified by **4 things**:
  - Server IP
  - Server port (e.g. 8080)
  - Client IP
  - Client port (a random high number assigned by the client OS)
- Two clients connecting to the same port = two different sockets (different client IP/port)
- **Analogy**: Port = published phone number. Socket = an actual live phone call.

---

## 3. localhost vs Real Network

- `localhost` (127.0.0.1) means "this same machine"
- Traffic to localhost **never leaves the computer** — handled by a virtual **loopback interface**
- The physical WiFi/ethernet card is **not involved**
- The network card only matters when traffic goes to a **different machine** (e.g. production)

---

## 4. BIO vs NIO (Tomcat)

| | BIO (old) | NIO (current) |
|---|---|---|
| Thread assigned | Immediately on connection | Only when data is ready |
| Thread during wait | Frozen waiting for bytes | Free, doing other work |
| Socket monitoring | One thread per socket | OS monitors all sockets via `epoll`/`select` |

- NIO uses an **acceptor thread** that asks the OS: *"wake me up when any socket has data ready"*
- OS does the actual monitoring — acceptor thread just reacts to notifications
- Once data is ready, a **worker thread** from the pool is assigned

> **Important**: NIO's non-blocking behaviour only applies to the socket/network layer. Once the request reaches your Spring MVC code, everything is still blocking.

---

## 5. Tomcat Thread Pool (nio-8080-exec-*)

- Tomcat and Spring Boot run in **one process** — there is only **one thread pool**
- A single **acceptor thread** monitors all sockets (not from the pool)
- When a socket has data ready, one worker thread from the pool handles **everything**:
  1. Read raw bytes off socket
  2. Parse into HTTP request
  3. Run Spring Security filters
  4. Route to controller
  5. Run business logic
  6. Call Hibernate, wait for DB
  7. Serialize response to JSON
  8. Write bytes back to socket
  9. Return to pool
- Default pool size: **200 threads**
- Configurable via:
  ```properties
  server.tomcat.threads.max=200
  server.tomcat.threads.min-spare=10
  ```

---

## 6. Spring MVC vs Spring Boot

- **Spring Boot** is not a web framework — it is an opinionated launcher
- When you add `spring-boot-starter-web`, Spring Boot auto-configures:
  - **Spring MVC** as the web layer
  - **Embedded Tomcat** as the server
- All your `@RestController`, `@GetMapping` etc. are **Spring MVC** annotations
- To switch to reactive: use `spring-boot-starter-webflux` instead (uses Netty)

---

## 7. @Async — Second Thread Pool

- `@Async` lets you offload work to a **separate thread pool** you opt into explicitly
- The Tomcat worker thread submits the task and **returns immediately** to the pool
- The async task runs on a different thread in the background
- Good for: fire-and-forget tasks (emails, notifications, background jobs)
- **Not good for**: when the controller needs the result — you'd block waiting anyway
- Does not fully solve the blocking problem — just moves it

---

## 8. WebFlux — Fully Non-Blocking

- Uses a small **event loop thread pool** — typically **one thread per CPU core**
- Threads **never block** — they register a callback and move on immediately
- `Mono<T>` = a promise of a single future value
- `Flux<T>` = a promise of a stream of future values

```java
// Blocking (Spring MVC)
User user = userRepository.findById(id); // thread frozen here

// Non-blocking (WebFlux)
userRepository.findById(id)             // returns immediately
  .map(user -> new UserResponse(user))  // runs when data arrives
```

- **Throughput**: 4 event loop threads can handle thousands of concurrent requests vs 200 Tomcat threads handling ~400 req/sec
- **Catch**: Entire chain must be non-blocking. One blocking call freezes a precious event loop thread. Code is harder to read and debug.

---

## 9. JavaScript Event Loop

- JavaScript is **single threaded** — always, no exceptions
- Uses an **event loop** model:
  1. Slow operations (fetch, DB) are handed off to the **OS**
  2. JS thread moves on immediately
  3. OS completes the work, puts callback in the **callback queue**
  4. Event loop picks up callback when call stack is empty
- Never blocks — but CPU intensive work **freezes the entire application**
- Node.js uses **Worker Threads** for CPU heavy work as an explicit opt-in

---

## 10. Mono vs Promise — They Are the Same Idea

```javascript
// JavaScript Promise
fetch("/api/users")
  .then(user => doSomething(user))

// Java WebFlux Mono
userRepository.findById(id)
  .map(user -> doSomething(user))
```

Both:
- Represent a **future value**
- Let you chain what happens when the value arrives
- Do not block the current thread

**Difference**: JS has one thread so no race conditions. WebFlux has multiple event loop threads so shared mutable state can still cause concurrency bugs.

---

## 11. Java vs Node.js for Backend

| | Java | Node.js |
|---|---|---|
| CPU intensive work | Real threads, runs in parallel | Blocks single thread |
| Type safety | Strong static typing, compiler catches bugs | Dynamic (TypeScript helps but not as strict) |
| Ecosystem maturity | 25+ years, massive enterprise ecosystem | Younger, huge npm ecosystem |
| Code simplicity | More verbose | Faster to build simple APIs |
| Team flexibility | Separate frontend/backend | Same language for both |
| Concurrency model | Thread pool (MVC) or event loop (WebFlux) | Single threaded event loop |

**Honest answer**: For most CRUD backends both are comparable. Choice usually comes down to team familiarity, company history, and hiring — not pure technical merit.

---

## Key Takeaways

- NIO = non-blocking at the **socket layer only** in Spring MVC
- One thread pool, one thread does the full request lifecycle end to end
- `@Async` offloads fire-and-forget work but doesn't solve blocking fundamentally
- WebFlux solves blocking all the way through but at the cost of complexity
- JavaScript's event loop and WebFlux's Mono/Flux are the same concept
- `localhost` never touches your network card — it's all internal
- Port = address label. Socket = live connection object.
