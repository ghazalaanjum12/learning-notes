# JPA & Spring Security — Revision Notes

## 1. `@Entity` vs `@Table`

| | `@Entity` | `@Table` |
|---|---|---|
| Purpose | Marks class as persistable, managed by JPA | Configures the underlying table (name, schema, constraints) |
| Required? | Yes | No — optional |
| Without it | Class isn't managed by JPA at all | Table name defaults to the class name |

```java
@Entity
@Table(name = "app_users", schema = "public",
       uniqueConstraints = @UniqueConstraint(columnNames = "username"))
public class User { ... }
```

## 2. `@JoinColumn` and Relationship Annotations

### What `@JoinColumn` does
Names the **actual foreign-key column** in the database table for this entity — i.e. which column stores the ID pointing to the referenced entity.

```java
@ManyToOne
@JoinColumn(name = "follower_id")   // "the follower field is backed by the follower_id column"
private User follower;
```

Without it, JPA guesses a default column name (usually not what you want).

### The core question for choosing a relationship type
> **Can the same foreign-key value repeat across multiple rows in this table?**

- **Yes, it can repeat** → `@ManyToOne` (many rows here can point to the same one row there)
- **No, it must be unique** (enforced via unique constraint) → `@OneToOne`
- **Both sides can repeat** → `@ManyToMany` (needs a join table)

### Examples

**`@ManyToOne`** — Many `Email` rows can belong to the same `Employee`:
```java
@Entity
public class Email {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "employee_id")
    private Employee employee;
}
```
`employee_id = 55` can appear in many rows (one employee, many emails).

**`@OneToOne`** — Each `Office` points to exactly one `Address`, and vice versa (enforced by a unique constraint on the FK column):
```java
@Entity
public class Office {
    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "addressId")
    private Address address;
}
```
> Note: `@OneToOne` defaults to `EAGER` fetch. True lazy loading on `@OneToOne` needs bytecode enhancement, or it silently loads eagerly anyway.

### Self-referencing many-to-many pattern: `Follow` entity
Models "user follows user" — a relationship *between* two rows of the same entity, not a property of one row.

```java
@Entity
@Table(name = "follows",
       uniqueConstraints = @UniqueConstraint(columnNames = {"follower_id", "followed_id"}))
public class Follow {
    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @ManyToOne
    @JoinColumn(name = "follower_id")
    private User follower;   // the person doing the following

    @ManyToOne
    @JoinColumn(name = "followed_id")
    private User followed;   // the person being followed
}
```

- Many `Follow` rows can share the same `follower_id` (one user follows many people) → `@ManyToOne`.
- Many `Follow` rows can share the same `followed_id` (one user has many followers) → `@ManyToOne`.
- A **unique constraint** on `(follower_id, followed_id)` prevents duplicate follows — simpler than a composite primary key.

### Alternative: composite primary key with `@IdClass`
Instead of a surrogate `id` + unique constraint, you *can* make the pair itself the primary key:

```java
@Entity
@IdClass(FollowId.class)
public class Follow {
    @Id @ManyToOne @JoinColumn(name = "follower_id") private User follower;
    @Id @ManyToOne @JoinColumn(name = "followed_id") private User followed;
}
```
Requires a companion `FollowId` class (matching field names/types, `equals()`/`hashCode()`, no-args constructor) to represent the combined identity.

**Trade-off:** more "correct" relationally, but adds real complexity for a beginner (composite key repositories, custom `equals`/`hashCode`). A surrogate `id` + unique constraint achieves the same duplicate-prevention with far less ceremony — generally the better starting choice.

## 3. Derived Query Methods (Spring Data JPA)

Method names are parsed as **property traversals on entity fields**, not raw database columns.

```java
boolean existsByFollowerIdAndFollowedId(UUID followerId, UUID followedId);
```

- `Follow` has no field literally called `followerId`.
- It has a field `follower` (type `User`). Spring Data traverses into `User` and finds `id`.
- So `FollowerId` → `follower.id` — equivalent to `follow.getFollower().getId()` in plain Java.

**Generated JPQL:**
```sql
SELECT CASE WHEN COUNT(f) > 0 THEN true ELSE false END
FROM Follow f
WHERE f.follower.id = :followerId AND f.followed.id = :followedId
```

**Translated SQL (what actually hits the DB):**
```sql
SELECT CASE WHEN COUNT(f.id) > 0 THEN true ELSE false END
FROM follows f
WHERE f.follower_id = ? AND f.followed_id = ?
```
No join to `users` needed — the FK columns already live on `follows`.

### Handy `FollowRepository` methods
```java
@Repository
public interface FollowRepository extends CrudRepository<Follow, UUID> {
    boolean existsByFollowerIdAndFollowedId(UUID followerId, UUID followedId);
    Optional<Follow> findByFollowerIdAndFollowedId(UUID followerId, UUID followedId);
    void deleteByFollowerIdAndFollowedId(UUID followerId, UUID followedId);
}
```
`save()` and `delete()` come free from `CrudRepository` — no need to write them.

⚠️ If using `@IdClass(FollowId.class)` instead of a surrogate ID, the repository must be `CrudRepository<Follow, FollowId>`.

## 4. Handling `null` / Anonymous Users Safely

**Danger:** `existsByFollowerIdAndFollowedId(null, targetId)` generates `WHERE follower_id = NULL` in SQL — always evaluates to false (SQL null semantics), so it "accidentally" works but doesn't clearly communicate intent.

**Better:** explicitly branch before querying:
```java
boolean isFollowing = currentUser != null
    && followRepository.existsByFollowerIdAndFollowedId(currentUser.getId(), targetUser.getId());
```

### The `AnonymousAuthenticationToken` gotcha
For unauthenticated requests, Spring Security does **not** leave `SecurityContextHolder.getContext().getAuthentication()` as `null`. It substitutes an `AnonymousAuthenticationToken`, whose principal is typically the string `"anonymousUser"` — not `null`, and not your `User` type.

```java
Authentication authentication = SecurityContextHolder.getContext().getAuthentication();

if (authentication == null
    || !authentication.isAuthenticated()
    || authentication instanceof AnonymousAuthenticationToken) {
    return Optional.empty();
}

Object principal = authentication.getPrincipal();
if (principal instanceof User user) {
    return Optional.of(user);   // safe pattern match — no ClassCastException if principal isn't a User
}
```

## 5. `AuthenticationFacade` Pattern

**Why a `@Component` (facade) rather than a `static` utility class:**
- Static methods (e.g. `AuthUtils.getCurrentUser()`) are hard to mock cleanly in unit tests (Mockito needs `MockedStatic`).
- A `@Component` can be injected and mocked normally:
  ```java
  @Mock private AuthenticationFacade authenticationFacade;
  when(authenticationFacade.getCurrentUser()).thenReturn(Optional.of(testUser));
  ```

**`Service` vs `Facade` naming:**
- `Service` implies business logic / decision-making.
- `Facade` implies "simplified wrapper hiding an awkward API" — no business logic of its own.
- Functionally identical to Spring (`@Service` is just `@Component` with a label) — the difference is purely about signaling intent to future readers.

**Consolidated facade example** — wraps both login authentication and current-user lookup, keeping all direct Spring Security API calls (`AuthenticationManager`, `SecurityContextHolder`) in one place:

```java
@Component
@RequiredArgsConstructor
public class AuthenticationFacade {

    private final AuthenticationManager authenticationManager;

    public User authenticate(String email, String password) {
        Authentication authResult = authenticationManager.authenticate(
            new UsernamePasswordAuthenticationToken(email, password)
        );
        return (User) authResult.getPrincipal();
    }

    public Optional<User> getCurrentUser() {
        Authentication authentication = SecurityContextHolder.getContext().getAuthentication();

        if (authentication == null
            || !authentication.isAuthenticated()
            || authentication instanceof AnonymousAuthenticationToken) {
            return Optional.empty();
        }

        Object principal = authentication.getPrincipal();
        if (principal instanceof User user) {
            return Optional.of(user);
        }

        return Optional.empty();
    }
}
```

**Folder placement:** no need for a dedicated `facade` package for one or two classes — keep it in the existing `service` package unless/until multiple facades accumulate.

### `UsernamePasswordAuthenticationToken` — two roles
- **Login flow (2-arg constructor):** `new UsernamePasswordAuthenticationToken(email, password)` — "unauthenticated, please verify these credentials."
- **Post-JWT-validation (3-arg constructor, includes authorities):** built by the JWT filter after verifying the token — "already authenticated, here's the confirmed principal."
- The 2 vs 3 argument constructor is how Spring Security internally marks a token as authenticated or not.

Typical JWT filter flow:
```java
UserDetails userDetails = userDetailsService.loadUserByUsername(email);

UsernamePasswordAuthenticationToken authToken =
    new UsernamePasswordAuthenticationToken(userDetails, null, userDetails.getAuthorities());

SecurityContextHolder.getContext().setAuthentication(authToken);
```

## 6. Spring Security — `authorizeHttpRequests` Matchers

- `requestMatchers(url1, url2, ...)` **without** an `HttpMethod` matches **all** HTTP methods on those paths.
- Scope by method when different HTTP verbs on the same path need different rules:

```java
.authorizeHttpRequests(auth -> auth
    .requestMatchers(HttpMethod.POST, basePath + "/users", basePath + "/users/login").permitAll()
    .requestMatchers(HttpMethod.GET, basePath + "/profiles/{username}").permitAll()
    // ... other rules, then authenticated() catch-all
)
```

- Path variables (`{username}`) work in matchers exactly like in `@GetMapping` — match a single path segment. The variable *name* doesn't need to match your controller's variable name; Security only cares it's a wildcard segment.
- `/profiles/{username}` matches `/profiles/alice` but **not** `/profiles/alice/extra`.

## Quick Reference: Choosing a Relationship Annotation

Ask: **"Looking at the foreign-key column, can the same value appear in more than one row?"**

| Can repeat? | Annotation |
|---|---|
| Yes, on this side only | `@ManyToOne` |
| No (unique constraint) | `@OneToOne` |
| Yes, on both sides | `@ManyToMany` (needs join table) |
