# Validation in Spring Boot with OpenAPI Generated Code

## The Problem

When OpenAPI generates model classes like `UpdateUser`, semantic constraints like _"at least one field is required"_ are only expressed as **documentation comments** — they are not enforced by the generated code. All fields are either `@Nullable` or `JsonNullable.undefined()`, so an empty request body `{}` passes validation silently.

---

## The Three Approaches

### 1. Validator Called in the Delegate or Service

A plain Spring `@Component` that contains the validation logic, called explicitly.

```java
@Component
public class UpdateUserValidator {

    public void validate(UpdateUser user) {
        if (user == null) {
            throw new ResponseStatusException(
                HttpStatus.UNPROCESSABLE_ENTITY,
                "Request body must not be null"
            );
        }

        boolean hasAtLeastOneField = user.getEmail() != null
            || user.getPassword() != null
            || user.getUsername() != null
            || user.getBio().isPresent()
            || user.getImage().isPresent();

        if (!hasAtLeastOneField) {
            throw new ResponseStatusException(
                HttpStatus.UNPROCESSABLE_ENTITY,
                "At least one field must be provided"
            );
        }
    }
}
```

**Where to call it:**
- Prefer the **service layer** over the delegate — the delegate is a thin HTTP bridge, business rules belong in the service.

```java
@Service
@RequiredArgsConstructor
public class UserService {
    private final UpdateUserValidator updateUserValidator;

    public User updateUser(UpdateUser update) {
        updateUserValidator.validate(update); // semantic validation
        // ... business logic
    }
}
```

**Pros:**
- Generated code is untouched
- Easy to unit test
- Explicit and readable

**Cons:**
- Must remember to call it manually
- Not triggered by `@Valid`

---

### 2. Class-Level Custom Constraint Annotation

Create a custom annotation that integrates with Bean Validation, so it fires automatically whenever `@Valid` is used.

**Step 1 — Define the annotation:**

```java
@Target({ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = AtLeastOneFieldValidator.class)
public @interface AtLeastOneField {
    // These three methods are mandatory boilerplate for any Bean Validation annotation
    String message() default "At least one field must be provided";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

**Step 2 — Write the validator:**

```java
public class AtLeastOneFieldValidator
        implements ConstraintValidator<AtLeastOneField, UpdateUser> {

    @Override
    public boolean isValid(UpdateUser user, ConstraintValidatorContext ctx) {
        if (user == null) return true; // let @NotNull handle null separately

        return user.getEmail() != null
            || user.getPassword() != null
            || user.getUsername() != null
            || user.getBio().isPresent()
            || user.getImage().isPresent();
    }
}
```

**Step 3 — Annotate the model class:**

```java
@AtLeastOneField
public class UpdateUser { ... }
```

**Pros:**
- Fires automatically with `@Valid` — no manual calls
- Reusable across any endpoint using `UpdateUser`
- Integrates with Spring's standard validation error handling

**Cons:**
- Requires modifying the generated `UpdateUser` class (breaks on regen)
- More boilerplate upfront

---

### 3. `RequestBodyAdvice`

A Spring hook that intercepts the deserialized request body **before** it reaches the controller, automatically, for a specific request type.

```java
@ControllerAdvice
public class UpdateUserRequestBodyAdvice extends RequestBodyAdviceAdapter {

    @Override
    public boolean supports(MethodParameter parameter, Type targetType,
            Class<? extends HttpMessageConverter<?>> converterType) {
        return targetType.equals(UpdateCurrentUserRequest.class);
    }

    @Override
    public Object afterBodyRead(Object body, HttpInputMessage inputMessage,
            MethodParameter parameter, Type targetType,
            Class<? extends HttpMessageConverter<?>> converterType) {

        UpdateCurrentUserRequest request = (UpdateCurrentUserRequest) body;
        UpdateUser user = request.getUser();

        boolean hasAtLeastOneField = user.getEmail() != null
            || user.getPassword() != null
            || user.getUsername() != null
            || user.getBio().isPresent()
            || user.getImage().isPresent();

        if (!hasAtLeastOneField) {
            throw new ResponseStatusException(
                HttpStatus.UNPROCESSABLE_ENTITY,
                "At least one field must be provided"
            );
        }

        return body;
    }
}
```

**Pros:**
- Fully automatic — no changes to delegate or service
- Keeps generated code untouched

**Cons:**
- Overkill for a single endpoint
- Harder to unit test in isolation
- Less discoverable — behaviour is implicit

## Comparison Table

| | Validator in Service | Class-Level Constraint | `RequestBodyAdvice` |
|---|---|---|---|
| Explicit call needed | Yes | No | No |
| Works with `@Valid` | No | Yes | No |
| Touches generated code | No | Yes | No |
| Easy to unit test | Yes | Yes | Harder |
| Good for reuse | Manual | Automatic | Per request type |
| Discoverability | High | Medium | Low |

## Industry Standard & Best Practice

### For simple field validation
Use `@Valid` + Bean Validation annotations (`@NotBlank`, `@Email`, `@Size`). In OpenAPI projects, these are ideally **generated from the spec** automatically.

### For cross-field / semantic validation
> _"At least one field required", "if X then Y must also be set"_

These are **business rules**, not data constraints. The industry standard is to handle them in the **service layer**, not the delegate.

The delegate's only job is to bridge HTTP to the service and return a response. Business rules belong one level deeper.

### Two-Layer Pattern (most common in OpenAPI projects)

```
HTTP Request
    → @Valid (field-level constraints from spec, auto-generated)
    → Delegate (thin layer, no logic)
    → Service (semantic/business validation + business logic)
```

---

## Key Takeaways

- OpenAPI generators do **not** enforce semantic constraints like "at least one field" — only field-level annotations
- `@Valid` only triggers **Bean Validation annotations** — a plain validator class won't be called by it
- Prefer **service-layer validation** for cross-field business rules in generated-code projects
- Reserve **custom constraint annotations** for rules that repeat across many endpoints and justify the boilerplate
- `RequestBodyAdvice` is a valid but advanced tool — best suited for cross-cutting concerns like logging or decryption, not single-endpoint business rules
