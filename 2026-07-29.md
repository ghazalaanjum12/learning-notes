# JPA + Lombok Revision Notes — Conduit Project

## 1. Constructors in JPA Entities

**Rule: JPA requires a no-arg constructor.** Hibernate instantiates entities via **reflection** when hydrating rows from the DB, and reflection uses the no-arg constructor to create an empty shell before populating fields.

- Can be `public` or `protected`. `protected` is conventional — signals "for JPA/framework use," discourages app code from calling `new Entity()` directly and getting a null-filled object.
- **Java's implicit constructor rule:** if a class defines **zero** constructors, Java auto-generates a `public` no-arg one for free. The moment you add **any** constructor yourself, that free one disappears — you must add the no-arg one explicitly from then on.

```java
protected User() {}                 // required by JPA
public User(String email) { ... }   // your own, for real object creation
```

## 2. Lombok Constructor Annotations

| Annotation | Includes | Notes |
|---|---|---|
| `@NoArgsConstructor` | nothing | satisfies JPA's requirement |
| `@RequiredArgsConstructor` | fields marked `final` or `@NonNull` | skips everything else (e.g. auto-generated `id`) |
| `@AllArgsConstructor` | **every** field, in declaration order | includes `id` too — usually awkward for `@GeneratedValue` entities |
| `@Builder` | named-field construction | **suppresses the implicit no-arg constructor** — must pair with `@NoArgsConstructor` explicitly or JPA hydration breaks |

**Why fields can't be `final` on entities:** a `final` field must be assigned in *every* constructor, including the no-arg one JPA needs. That's incompatible — you'd have to fake-assign it (`this.x = null`), defeating the purpose. Use `@NonNull` instead — Lombok treats `final`/`@NonNull` fields the same way for constructor generation, without the compile-time immutability constraint.

```java
@NoArgsConstructor          // protected Follow() {}         — for JPA
@RequiredArgsConstructor    // public Follow(User a, User b) — for you
public class Follow {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;               // excluded (not final/@NonNull)

    @NonNull @ManyToOne @JoinColumn(name = "follower_id")
    private User follower;         // included

    @NonNull @ManyToOne @JoinColumn(name = "followed_id")
    private User followed;         // included
}
```

### `@NonNull` (Lombok) vs `@NotNull`/`@NotEmpty` (Jakarta Bean Validation)

| | `@NonNull` (Lombok) | `@NotNull`/`@NotEmpty` (Jakarta) |
|---|---|---|
| What it is | Code generator instruction | Validation metadata, needs a validator to act on it |
| When it fires | Inside the specific generated constructor/setter, at call time | Wherever validation is triggered: `@Valid` on controllers, Bean Validation framework, `@PrePersist`/`@PreUpdate` via Hibernate Validator |
| Throws | `NullPointerException` | `ConstraintViolationException` (or 400 response in Spring MVC) |
| Checks | null only | `@NotNull`: null only. `@NotEmpty`: null **and** empty string/collection |
| Bypassed by | Hibernate setting fields directly via reflection | Nothing — enforced wherever validation actually runs |

They're complementary, not interchangeable — use `@NonNull` for a fast fail in your own construction code, Bean Validation for request/DTO validation, `@Column(nullable = false)` for the DB-level guarantee (see below).

## 3. `@Column(nullable = false, unique = true)` vs `@NonNull`

Two completely different layers — use **both**, not one instead of the other.

| | `@Column(nullable=false, unique=true)` | `@NonNull` (Lombok) |
|---|---|---|
| Enforced by | The database itself | Your Java code, one method at a time |
| Catches | Bad data from *any* source (app, script, migration, another service) | Only calls to that specific generated constructor/setter |
| Failure | SQL constraint violation | `NullPointerException` |
| Timing | At `INSERT`/`UPDATE` | At object construction |

`@NonNull` = fast, early, in-process failure. `@Column(nullable=false)` = the actual guarantee that bad data can never land in the DB, regardless of path.

## 4. Reflection (why JPA needs a no-arg constructor at all)

**Reflection** = Java's ability to inspect/instantiate classes and read/set fields **at runtime, by name**, instead of through normal compiled code.

```java
Class<?> clazz = Class.forName("com.conduit.entity.User");
Object instance = clazz.getDeclaredConstructor().newInstance(); // no-arg ctor
Field emailField = clazz.getDeclaredField("email");
emailField.setAccessible(true);
emailField.set(instance, "a@b.com");   // direct field write, bypasses setters entirely
```

Hibernate is a generic library — it doesn't have `new User(...)` written for your specific class. At runtime it: looks up your entity class → calls the no-arg constructor via reflection → sets each column's value directly onto the matching field, bypassing your constructors/setters entirely. This is also why `final` fields don't work well on entities: direct field-write via reflection doesn't go through a constructor, so `final`'s "must assign during construction" rule doesn't fit the pattern.

*(SAP Commerce Cloud comparison: similar underlying mechanism to what a HAC Groovy script exploits deliberately for dynamic access — but here, reflection is invisible framework plumbing operating on an ordinary, statically-typed Java class you never intended to be dynamic.)*

## 5. Entity Relationships

### Unidirectional vs Bidirectional

**Unidirectional** (`Article` → `User` only) is often enough — valid JPA, simplest to reason about:
```java
@ManyToOne
@JoinColumn(name = "author_id", nullable = false)
private User author;
```

**Bidirectional** — add the inverse side only if you need `user.getArticles()` in Java code:
```java
@OneToMany(mappedBy = "author")
private List<Article> articles = new ArrayList<>();
```
- `mappedBy` points at the **field name** on the owning side, not a column name.
- The `@ManyToOne` side (`Article.author`) **owns** the FK column. The `@OneToMany` side is a **read-only derived view** — Hibernate builds it with `SELECT ... WHERE author_id = ?`, no second column exists for it.
- **Trap:** `user.getArticles().add(article)` persists **nothing** — you must set the owning side (`article.setAuthor(user)`) for the FK to actually be written. Fix with a sync helper:
```java
public void addArticle(Article article) {
    articles.add(article);
    article.setAuthor(this);
}
```
- **Serialization trap:** bidirectional relationships can cause infinite recursion (`user → articles → author → articles → ...`) if you serialize entities directly to JSON. Use DTOs, not raw entities, as API response types.

### Fetch defaults
- `@ManyToOne` → `FetchType.EAGER` by default (single related row, cheap).
- `@OneToMany` → `FetchType.LAZY` by default (potentially large collection, expensive) — **keep it lazy**.

### Cascade (`@OneToMany` side)
Reflects "does the child's lifecycle make sense without the parent?"
- `CascadeType.ALL` = `PERSIST, MERGE, REMOVE, REFRESH, DETACH` — deleting the parent deletes all children too. Risky for `User → Article` (deleting a user shouldn't necessarily wipe their articles).
- Safer subset for parent/child where child shouldn't be nuked automatically: `cascade = {CascadeType.PERSIST, CascadeType.MERGE}`.
- `orphanRemoval = true` — removing a child *from the collection* (not deleting the parent) deletes it from the DB. Only pair this with `REMOVE`/`ALL` cascade.
- Never cascade `PERSIST`/`REMOVE` from the `@ManyToOne` side (`Article.author`) — saving/deleting an article shouldn't create/delete a `User`.

## 6. Timestamps: `@CreationTimestamp` / `@UpdateTimestamp`

Hibernate-specific (not standard JPA — `org.hibernate.annotations`), auto-populate timestamp fields without manual `service.setCreatedAt(...)` calls scattered everywhere.

```java
@CreationTimestamp
@Column(name = "created_at", updatable = false)
private Instant createdAt;   // set once, at INSERT

@UpdateTimestamp
@Column(name = "updated_at")
private Instant updatedAt;   // set on every INSERT and UPDATE
```

**Gotcha:** these don't make the field immutable from Java — if you have a blanket Lombok `@Setter` on the class, app code can still call `.setCreatedAt(...)` and Hibernate will happily persist it on next flush. Fix: exclude these fields from Lombok setter generation (`@Setter(AccessLevel.NONE)` on the field).

**`Instant` (java.time):** a single point on the UTC timeline (nanoseconds since Unix epoch), no timezone/calendar concept attached — unlike `LocalDateTime` (ambiguous, no TZ info) or `ZonedDateTime` (point in time + explicit TZ). Ideal for `createdAt`/`updatedAt`: unambiguous, DST-proof, maps cleanly to DB `TIMESTAMP` columns, and serializes to ISO-8601 UTC (`"2026-07-29T14:32:10.123Z"`) matching OpenAPI's `date-time` format.

## 7. Slugs

A slug = URL-friendly identifier derived from the title (lowercase, hyphenated, punctuation stripped) — used in routes like `GET /api/articles/:slug` instead of exposing a raw title or opaque UUID.

**Generate via `@PrePersist`** (a JPA lifecycle callback — runs automatically right before INSERT, no repository/service boilerplate needed):

```java
@PrePersist
private void generateSlug() {
    if (slug == null || slug.isBlank()) {
        this.slug = slugify(title) + "-" + UUID.randomUUID().toString().substring(0, 8);
    }
}

private String slugify(String input) {
    return input.toLowerCase().trim()
            .replaceAll("[^a-z0-9\\s-]", "")
            .replaceAll("\\s+", "-")
            .replaceAll("-+", "-");
}
```

- Random suffix avoids collisions cheaply without an entity reaching into a repository (entities shouldn't call repositories/services).

**Industry-standard approach: generate once, never regenerate on title update.** Don't add `@PreUpdate` for slug — editing the title shouldn't silently break bookmarked/shared URLs. This matches WordPress, Dev.to, Medium, Shopify handles, etc. If a slug update is ever wanted, it should be an explicit user action, not an automatic side effect of a title edit.

## 8. Computed / Relative Fields: `favorited` vs `favoritesCount`

Neither belongs as a stored column on `Article` — both are derived at the DTO-mapping layer from a `Favorite` join entity.

- **`favorited`** — relative to *the current requester*: "did **this specific user** favorite this article?" Different value per viewer, same article.
- **`favoritesCount`** — absolute: total number of users who favorited the article. Same value for every viewer.

### `Favorite` entity (same shape as `Follow`)
```java
@Entity
@Table(name = "favorites",
        uniqueConstraints = @UniqueConstraint(columnNames = {"user_id", "article_id"}))
@NoArgsConstructor
@RequiredArgsConstructor
public class Favorite {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @NonNull @ManyToOne @JoinColumn(name = "user_id")
    private User user;

    @NonNull @ManyToOne @JoinColumn(name = "article_id")
    private Article article;
}
```
Unique constraint prevents double-favoriting from silently inflating the count. Pair with an `existsBy...` check in the service layer before insert, rather than relying on the DB constraint as the only defense.

### Avoiding N+1

`favoriteRepository.countByArticle(article)` and a hand-written `@Query("SELECT COUNT(f) FROM Favorite f WHERE f.article = :article")` are **identical** — Spring Data derives the same JPQL from the method name. No difference between them.

**The real N+1 risk** is calling a per-entity query **inside a loop** over a list:
```java
// BAD: 1 query for articles + N queries, one per article
for (Article article : articles) {
    long count = favoriteRepository.countByArticle(article);
}
```

**Fix — batch into one grouped query** when rendering a list/feed:
```java
@Query("SELECT f.article.id, COUNT(f) FROM Favorite f WHERE f.article IN :articles GROUP BY f.article.id")
List<Object[]> countByArticles(@Param("articles") List<Article> articles);
```
Build a `Map<UUID, Long>` from the result once, look up counts while building DTOs. Total: 2 queries regardless of list size.

For a **single-article page**, `countByArticle(article)` once is completely fine — no loop, no N+1 risk.

## 9. Query Method Derivation Patterns (Spring Data)

```java
// Nested property traversal: follower has no field "id" directly,
// but Follow.follower -> User.id resolves via property nesting
boolean existsByFollowerIdAndFollowedId(UUID followerId, UUID followedId);

// Direct property match: follower/followed ARE fields on Follow.
// Passing entity objects compares by extracted id, not full object equality.
Optional<Follow> findByFollowerAndFollowed(User follower, User followed);
```

**Caveat on entity-typed params:** the `User` objects passed in must have `id` populated (doesn't need to be fully loaded — a reference/detached object with just `id` set works). Passing a transient `User` with `id == null` silently matches nothing rather than erroring — a subtle bug to watch for.

Derived deletes also work: `void deleteByUserAndArticle(User user, Article article);` — useful for "unfavorite"/"unfollow" endpoints without loading the entity first.

## 10. Exceptions

Don't duplicate what `RuntimeException` already gives you for free (`getMessage()`):

```java
// Minimal, correct — no redundant field
public class ProfileNotFoundException extends RuntimeException {
    public ProfileNotFoundException(String message) {
        super(message);
    }
}
```

Only add your own field(s) when carrying **structured data beyond the message string** (e.g. the actual handle/id that wasn't found, for an exception handler to use without re-parsing text):

```java
public class ProfileNotFoundException extends RuntimeException {
    private final String handle;

    public ProfileNotFoundException(String handle) {
        super("Profile not found: " + handle);
        this.handle = handle;
    }

    public String getHandle() { return handle; }
}
```
