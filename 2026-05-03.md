# OpenAPI Generator + Spring Boot — Study Notes

## 1. What is OpenAPI Generator (Server Stubs)?

When you have an OpenAPI spec (`.yml`), the OpenAPI Generator Maven plugin can generate:
- **Model classes** — Java POJOs for your request/response bodies
- **Controller interfaces** — Spring MVC controllers with all routes pre-mapped
- **Delegate interfaces** — where you write your actual business logic

This means you never write boilerplate controller code — you just implement the delegate.

## 2. Key Dependencies and Why They're Needed

### `jackson-databind-nullable`
- Introduces the `JsonNullable<T>` wrapper type
- Solves the problem of distinguishing between a field being **absent** vs **explicitly null** in JSON
- Required when your OpenAPI spec uses `nullable: true` or `type: [string, 'null']`
- Not managed by the Spring Boot BOM — always specify the version explicitly:
```xml
<dependency>
    <groupId>org.openapitools</groupId>
    <artifactId>jackson-databind-nullable</artifactId>
    <version>0.2.8</version>
</dependency>
```

### `springdoc-openapi-starter-webmvc-ui` (Spring Boot 3.x)
- Serves a live Swagger UI at `/swagger-ui.html`
- **Note:** The artifact name changed between versions:
  - Spring Boot 2.x → `springdoc-openapi-ui`
  - Spring Boot 3.x → `springdoc-openapi-starter-webmvc-ui`
- Always use the correct artifact for your Boot version — bumping version numbers alone won't fix a wrong artifact name

## 3. JsonNullable — Deep Dive

Plain Java `null` cannot distinguish between two different cases:

| Scenario | Plain `String` | `JsonNullable<String>` |
|---|---|---|
| Field not sent at all `{}` | `null` | `JsonNullable.undefined()` |
| Field explicitly null `{"bio": null}` | `null` | `JsonNullable.of(null)` |
| Field has value `{"bio": "Hello"}` | `"Hello"` | `JsonNullable.of("Hello")` |

This matters for **PATCH endpoints** — you need to know if the client wants to clear a field or just didn't mention it.

### Checking in service layer:
```java
if (updateUser.getBio().isPresent()) {
    // field was sent — update it (value might be null to clear it)
    existingUser.setBio(updateUser.getBio().get());
}
// if undefined(), skip — don't touch the field
```

## 4. `required` vs `nullable` in OpenAPI — They Are Different

These answer different questions:

- **`required`** → must the field be **present** in the JSON?
- **`nullable`** (`type: [string, 'null']`) → can the field's **value** be null?

A field can be both required AND nullable:
```yaml
User:
  required:
    - bio      # must be present in JSON
  properties:
    bio:
      type:
        - string
        - 'null'   # but its value can be null
```

Valid JSON: `{ "bio": null }` ✓  
Invalid JSON: `{}` (bio missing entirely) ✗

### Request vs Response asymmetry
Your spec intentionally differs:
- **`User` (response)** — `bio` and `image` are `required` — server must always send them
- **`UpdateUser` (request)** — nothing is required — client only sends what it wants to change

## 5. Why You Get `InlineObject` Classes

The generator creates `InlineObject1`, `InlineObject2`, etc. when schemas are defined **anonymously inline** instead of as named `$ref` components.

### Causes inline objects (bad):
```yaml
responses:
  UserResponse:
    content:
      application/json:
        schema:
          type: object        # anonymous — generator invents a name
          properties:
            user:
              $ref: '#/components/schemas/User'
```

### Fix — move to named components:
```yaml
components:
  schemas:
    UserWrapper:              # now it has a name
      type: object
      properties:
        user:
          $ref: '#/components/schemas/User'

responses:
  UserResponse:
    content:
      application/json:
        schema:
          $ref: '#/components/schemas/UserWrapper'   # reference it
```

The generated code works either way, but named schemas produce much cleaner class names.

## 6. Managing Dependency Versions

### Spring Boot BOM
`spring-boot-starter-parent` manages hundreds of library versions for you. For any library it manages, **omit the version tag** and let Boot handle it.

Check what your Boot version manages at:
```
https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html
```

### For libraries outside the BOM (e.g. `jackson-databind-nullable`)
- Check the library's GitHub README for compatibility info
- Look at what transitive dependencies it pulls in and compare to your Boot version's expectations
- Pin the version explicitly in your pom

### Detecting conflicts
```bash
mvn dependency:tree
```
Look for lines marked `omitted for conflict` — these are version clashes you need to resolve.

## 7. The `@RequestMapping` Base Path

Generated controllers have this annotation:
```java
@RequestMapping("${openapi.realWorldConduit.base-path:/api}")
```

This is a Spring property placeholder with a default value. It means:
- Read `openapi.realWorldConduit.base-path` from `application.properties`
- If not defined, default to `/api`

So all your endpoints are prefixed with `/api` by default:
```
/api/users/login
/api/users
/api/user
```

## 8. Delegate Pattern

When using `delegatePattern=true` in the generator config, you must implement the delegate to get actual responses. Without it, endpoints return **501 Not Implemented** by default.

```java
@Service
public class UsersApiDelegateImpl implements UsersApiDelegate {
    @Override
    public ResponseEntity<UserResponse> login(LoginUserRequest body) {
        // your business logic here
    }
}
```

If you get **404** instead of 501, the controller isn't registered at all — see section 9.

## 9. Spring Boot Component Scan — Main Class Location

Spring Boot scans for components **starting from the package of your `@SpringBootApplication` class downward only**.

### Broken setup:
```
com.conduit
└── app
    └── ConduitApplication.java   ← scans com.conduit.app and below only
com.conduit.openapi.api           ← MISSED — not a sub-package of com.conduit.app
```

### Fixed setup:
```
com.conduit
└── ConduitApplication.java       ← scans com.conduit and everything below
com.conduit.openapi.api           ← picked up ✓
com.conduit.openapi.model         ← picked up ✓
```

**Rule of thumb:** Always place your main class at the root package with nothing else alongside it — it exists purely as the scan anchor.

### Note on `scanBasePackages`
```java
@SpringBootApplication(scanBasePackages = "com.conduit")
```
This is valid syntax but can still cause subtle issues because Spring Boot's auto-configuration uses the main class location as an anchor independently of `scanBasePackages`. Moving the main class to the root is the cleaner fix.

## 10. IntelliJ + Maven — Generated Sources Not Being Indexed

### The problem
After running a Maven build, `target/generated-sources` exists on disk but IntelliJ may not know about it — resulting in:
- No syntax highlighting in generated files
- Red squiggles on imports from generated code
- No autocomplete

### Why
IntelliJ maintains its own internal model of your project. It doesn't automatically watch `pom.xml` for changes — you have to explicitly tell it to reload.

### Fix
```
Right click pom.xml → Maven → Reload Project
```
or run:
```bash
mvn clean install
```
Then reload. IntelliJ will read the Maven config, discover `target/generated-sources` as a source root, and index everything.

### The `.class` vs source file confusion
- `target/generated-sources/...` — actual `.java` source files from the generator
- `target/classes/...` — compiled `.class` bytecode files

When IntelliJ opens a `.class` file it decompiles it with FernFlower ("decompiled file" banner at top). This is why the same class appears in two places and looks slightly different.

### When to always reload Maven in IntelliJ
- After adding/changing any dependency
- After changing plugin configuration
- After the OpenAPI spec changes and you regenerate
- After adding any code generation tool (Lombok, MapStruct, etc.)

## 11. Debugging a 404 Checklist

If you get a 404 hitting a generated endpoint:

1. **Check the full URL** — base path is `/api` by default, so `/api/users/login` not `/users/login`
2. **Check the port** — Spring Boot defaults to `8080`
3. **Verify generated sources are compiled** — run `mvn clean install`
4. **Reload Maven in IntelliJ** — so generated sources are indexed
5. **Check main class location** — must be at root package to scan everything
6. **Print all registered mappings** at startup to confirm routes exist:

```java
@SpringBootApplication
public class ConduitApplication {
    public static void main(String[] args) {
        var ctx = SpringApplication.run(ConduitApplication.class, args);
        var mappings = ctx.getBean(RequestMappingHandlerMapping.class);
        mappings.getHandlerMethods().forEach((k, v) -> System.out.println(k));
    }
}
```

If your route doesn't appear here, Spring never registered it — it's a scan/compile issue, not a routing issue.
