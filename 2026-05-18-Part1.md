# Spring Security & JWT — Revision Notes

---

## 1. ApplicationConfiguration

A configuration class that sets up the core authentication beans Spring Security needs.

### Key Beans

**`UserDetailsService`**
- Loads a user from the database by their email during authentication
- Throws `UsernameNotFoundException` if the user doesn't exist
- Spring Security calls this automatically during login

**`BCryptPasswordEncoder`**
- One-way hashing algorithm with a built-in salt
- Used to hash passwords on registration and verify them on login
- Never stores or compares plain-text passwords

**`AuthenticationManager`**
- Central coordinator of authentication
- Delegates to `AuthenticationProvider` to verify credentials
- Exposed as a bean so it can be injected into your login controller

**`AuthenticationProvider` (DaoAuthenticationProvider)**
- Wires `UserDetailsService` and `BCryptPasswordEncoder` together
- Fetches the user from the DB and verifies the password
- Returns an authenticated token if both checks pass

### Flow
```
Login Request
      │
      ▼
AuthenticationManager
      │  delegates to
      ▼
DaoAuthenticationProvider
      ├── UserDetailsService → fetch user by email from DB
      └── BCryptPasswordEncoder → verify password hash
```

## 2. SecurityConfiguration

Configures which requests are allowed, how users are authenticated, and where JWT validation fits in.

### Key Concepts

**CSRF disabled**
- CSRF attacks rely on browsers sending cookies/sessions automatically
- JWT APIs use tokens in headers, not cookies — so CSRF is not a threat

**URL Authorization**
```java
.requestMatchers("/api/users", "/api/users/login").permitAll()
.anyRequest().authenticated()
```
- Auth endpoints are public — no token needed
- Every other route requires a valid JWT

**Stateless Session**
```java
.sessionCreationPolicy(SessionCreationPolicy.STATELESS)
```
- Spring never creates or uses HTTP sessions
- Every request must carry its own JWT

**`authenticationProvider(authenticationProvider)`**
- Not a filter — just registers your `DaoAuthenticationProvider` with Spring Security
- Tells Spring to use YOUR provider when `authenticate()` is called, not its default

**`addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`**
- Inserts your JWT filter before Spring's built-in login filter
- Ensures JWT validation runs first on every request

### CORS Configuration
```java
configuration.setAllowedOrigins(List.of("http://localhost:8005"));
configuration.setAllowedMethods(List.of("GET", "POST"));
configuration.setAllowedHeaders(List.of("Authorization", "Content-Type"));
```
- Controls which frontend origins can talk to your API
- Without this, browsers block cross-origin requests by default

## 3. JwtAuthenticationFilter

Runs on every incoming request. Validates the JWT token and sets the security context.

### Step by Step

1. **Extract Authorization header** — if missing or doesn't start with `Bearer `, skip JWT processing and pass the request through (public routes)
2. **Extract JWT** — strip the `Bearer ` prefix with `substring(7)`
3. **Extract email** — decode the JWT and pull the email from its claims
4. **Check SecurityContext** — if already authenticated, skip (defensive check, always null in stateless setup)
5. **Load user from DB** — using `UserDetailsService.loadUserByUsername(email)`
6. **Validate token** — check it hasn't expired and belongs to this user
7. **Set authentication** — create a `UsernamePasswordAuthenticationToken` and set it in the `SecurityContextHolder`
8. **Continue** — pass the request down the filter chain

### Why `UsernamePasswordAuthenticationToken`?
- Despite the name, it's Spring Security's **general purpose authentication object**
- The JWT has already been validated — this token is just a "proof of authentication" stamp that Spring understands
- `null` credentials (password) because JWT already proved identity
- `SecurityContextHolder` doesn't understand JWT — only `Authentication` objects

### Why set the SecurityContext at all if stateless?
- It's reset on every request — nothing persists between requests
- But within a single request, Spring needs it populated so that:
  - `anyRequest().authenticated()` check passes
  - `@PreAuthorize` annotations work
  - You can access the current user via `SecurityContextHolder`

### Full Request Flow
```
Incoming Request
      │
      ▼
JwtAuthenticationFilter
      │
      ├── No Bearer token? → pass through (public route)
      │
      ├── Extract JWT → extract email
      │
      ├── Load user from DB
      │
      ├── Token valid? → set Authentication in SecurityContext
      │
      └── Continue to Controller
                  │
                  ▼
        Authorization check
                  │
          ├── authenticated? → reach Controller ✅
          └── not authenticated? → 403 Forbidden ❌
```

## 4. Login Flow

```java
public User authenticate(LoginUserDto input) {
    authenticationManager.authenticate(
        new UsernamePasswordAuthenticationToken(
            input.getEmail(),
            input.getPassword()
        )
    );
    return userRepository.findByEmail(input.getEmail()).orElseThrow();
}
```

- `authenticate()` is called purely for its **side effect** — verifying credentials
- If credentials are wrong → throws `AuthenticationException` → 401, method stops
- If correct → nothing returned, just continues
- User is then fetched separately to generate JWT (cleaner than casting the `Authentication` return value)
- `SecurityContext` is NOT set here — that only happens in `JwtAuthenticationFilter` on subsequent requests

## 5. Registration Flow

```java
public RegistrationResult registerUser(NewUser newUser) {
    User user = userMapper.newUserToUser(newUser);
    user.setHashPassword(passwordEncoder.encode(newUser.getPassword()));
    User savedUser = userRepository.save(user);
    String token = jwtService.generateToken(savedUser);
    return new RegistrationResult(savedUser, token);
}
```

- Password is hashed before saving — never store plain text
- Token is generated after saving so you have the persisted user object
- `User` implements `UserDetails` so it can be passed directly to `jwtService.generateToken()`

## 6. User Entity implementing UserDetails

```java
@Entity
public class User implements UserDetails {
    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return List.of();
    }

    @Override
    public String getPassword() { return this.hashPassword; }

    @Override
    public String getUsername() { return this.email; }

    @Override
    public boolean isAccountNonExpired() { return true; }

    @Override
    public boolean isAccountNonLocked() { return true; }

    @Override
    public boolean isCredentialsNonExpired() { return true; }

    @Override
    public boolean isEnabled() { return true; }
}
```

- Implementing `UserDetails` means your entity IS a `UserDetails` — no separate wrapper needed
- Can be passed directly anywhere Spring Security expects `UserDetails`

## 7. Java Records

A special class designed to be a pure immutable data carrier.

```java
public record RegistrationResult(User user, String token) {}
```

Automatically generates: constructor, getters, `equals()`, `hashCode()`, `toString()`

### Accessing members
```java
// Records use field name directly — no "get" prefix
result.user();   // ✅
result.token();  // ✅
result.getUser(); // ❌ doesn't exist
```

### When to use
- Returning multiple values from a method
- DTOs and request/response objects
- Any time you just need to group data and pass it around without modifying it

### When NOT to use
- JPA entities — need to be mutable
- Classes with business logic
- Classes that need inheritance

### Where to put them
- If used in one class only → define it inside that class
- If shared across multiple classes → put in `dto` package (not a `records` package — name by role, not by Java feature)

## 8. Circular Dependency

### The Problem
```
SecurityConfiguration
    → JwtAuthenticationFilter
        → UserDetailsService (bean defined IN SecurityConfiguration) ❌
```

`SecurityConfiguration` can't finish creating because `JwtAuthenticationFilter` needs `UserDetailsService`, which is defined inside `SecurityConfiguration` that hasn't finished being created yet.

### The Fix
Move `UserDetailsService` (and `PasswordEncoder`) into a separate `ApplicationConfiguration` class:

```
ApplicationConfiguration (UserDetailsService, PasswordEncoder)
        ↓
JwtAuthenticationFilter
        ↓
SecurityConfiguration ✅
```

## 9. Dynamic Base Path in Security Rules

If your controller uses a property-based base path:
```java
@RequestMapping("${openapi.realWorldConduit.base-path:/api}")
```

Your security rules must match:
```java
@Value("${openapi.realWorldConduit.base-path:/api}")
private String basePath;

.requestMatchers(basePath + "/users", basePath + "/users/login").permitAll()
```

## 10. Spring Bean Annotations

| Annotation | Purpose |
|---|---|
| `@Component` | Generic Spring-managed bean — use for infrastructure/cross-cutting concerns like filters |
| `@Service` | Business logic layer |
| `@Repository` | Data access layer |
| `@Controller` | Web layer |
| `@Configuration` | Contains bean definitions |

`@Service`, `@Repository`, `@Controller` are all specializations of `@Component` — they all register a bean but communicate intent. Use the most accurate one for the class's role.

## 11. Common Mistakes

| Mistake | Fix |
|---|---|
| `@Value("{property}")` not resolving | Must be `@Value("${property}")` — don't forget the `$` |
| 403 on public endpoints | Check `requestMatchers()` path matches actual endpoint path including base path |
| `securityFilterChain` won't compile | Add `throws Exception` to the method signature |
| No stateless session set | Add `SessionCreationPolicy.STATELESS` when using JWT |
| Field injection with `@Autowired` | Prefer constructor injection — more testable and explicit |
