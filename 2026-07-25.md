# Spring Security, Servlets & Networking — Revision Notes

## 1. String Formatting in Java

- `StringUtils` (both Spring's and Apache Commons') has **no** `{0}`/`{1}` style formatting — that's `MessageFormat` syntax, not `StringUtils`.
- **Industry standard for exception messages**: `String.format("...%s...", value)`
- `MessageFormat` with `{0}` → reserved mostly for i18n/locale-sensitive formatting.
- SLF4J `{}` placeholders → only for logging statements (`log.info("User {}", id)`), not exception messages.
- **Security note**: never interpolate sensitive data (e.g. passwords) into exception messages — they can end up in logs/stack traces/responses.

```java
throw new DuplicateUserException(
    String.format("User already registered with email %s", newUser.getEmail())
);
```

## 2. Lombok Logging

- `@Slf4j` generates `private static final Logger log = LoggerFactory.getLogger(ThisClass.class);` at compile time.
- Other variants: `@Log4j2`, `@CommonsLog`, `@Log` (java.util.logging) — `@Slf4j` is the right one for Spring Boot (default = Logback).

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class RegistrationService { ... }
```

### Do you need pom.xml changes?
- **No**, if using Logback (Spring Boot default) — `spring-boot-starter-logging` already bundles SLF4J + Logback.
- **Yes**, if switching to Log4j2 — must exclude `spring-boot-starter-logging` and add `spring-boot-starter-log4j2`, otherwise SLF4J complains about multiple bindings.

## 3. RealWorld/Conduit API Error Shape

Test assertions like:
```js
expect(res.body.errors.username[0]).to.eql("has already been taken");
```
expect a specific JSON shape (Rails/ActiveRecord validation-style):

```json
{
  "errors": {
    "username": ["has already been taken"],
    "email": ["has already been taken"]
  }
}
```

Key things to match: **field name as the key**, and the **exact message text**, not a custom message.

## 4. Networking Fundamentals

### IP Address, Port, Socket

| Concept | Analogy | Meaning |
|---|---|---|
| IP address | Street address of a building | Identifies the machine |
| Port | Apartment/unit number | Identifies which program on that machine (0–65535) |
| Socket | The open pipe/hallway between two specific parties | A live, bidirectional byte stream between two endpoints |

- A **port** doesn't "belong" to data — it's just a number a program binds to so the OS knows where to route incoming traffic (e.g. Tomcat on 8080, Postgres on 5432).
- A **socket** is the actual connection object. Sockets exist on **both ends**:
  - **Client (Postman)**: OS assigns a random **ephemeral port** (e.g. `54321`) automatically.
  - **Server (Tomcat)**: bound to the fixed port it's listening on (e.g. `8080`).
- A single TCP connection is uniquely identified by the 4-tuple:
  ```
  (client IP, client port, server IP, server port)
  ```
  This is why many simultaneous requests to the same server port don't collide — each has a different client port.
- `ServerSocket` (Tomcat's listening socket) just accepts new connections and hands off a fresh, dedicated `Socket` per client connection — the actual byte exchange happens on that per-connection socket, not the `ServerSocket` itself.

### From raw bytes to Java objects

An HTTP request is just **plain text** sent over the socket:
```
GET /api/user HTTP/1.1
Host: localhost:8080
Authorization: Token abc123
Accept: application/json

```

**Tomcat's job**: listen on a port → accept a socket connection → read raw bytes off it → parse them according to the HTTP text spec → construct Java objects (`HttpServletRequest`, `HttpServletResponse`) so your code never touches raw sockets/text directly.

```
Browser/Postman → TCP/HTTP bytes → Tomcat (servlet container) → HttpServletRequest/Response (Java objects) → your code
```

## 5. Servlets & Filters (the old Java EE spec, still underlying Spring Boot)

### Servlet
A Java class implementing `Servlet` (usually via `HttpServlet`) that handles requests/responses:

```java
public class MyServlet extends HttpServlet {
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) { ... }
}
```

- Predates Spring; very manual (no DI, no annotations, no routing conventions).
- Tomcat maintains a **registry**: URL pattern → Servlet instance (historically `web.xml`, now auto-configured by Spring Boot).

### Filter
A class that intercepts requests **before** they reach a servlet (and responses before they leave):

```java
public interface Filter {
    void doFilter(ServletRequest request, ServletResponse response, FilterChain chain);
}
```

- Used for cross-cutting concerns: logging, auth, CORS, compression.
- Filters chain together — each can inspect/reject/modify, or call `chain.doFilter(...)` to pass along.
- **Spring Security is implemented entirely as servlet Filters** (`FilterChainProxy`, `AnonymousAuthenticationFilter`, etc.) — this is why it runs *before* any Spring MVC / controller code.

### DispatcherServlet — the bridge to Spring MVC
- Spring Boot registers **exactly one real servlet**: `DispatcherServlet`, mapped to `/*`.
- Everything you know as "Spring MVC" (`@RestController`, `@GetMapping`, JSON serialization) is functionality `DispatcherServlet` provides on top of the raw servlet API.
- Your `@RestController` methods are **not** servlets themselves — `DispatcherServlet` is the one servlet; it uses reflection internally to find and invoke the right controller method.

### Full request pipeline

```
Tomcat (servlet container)
   ↓  accepts socket, parses raw bytes → HttpServletRequest/Response
Filter chain (Spring Security lives here — plain servlet Filters, runs FIRST)
   ↓
DispatcherServlet (the one real servlet — Spring MVC begins here)
   ↓
HandlerMapping → your @RestController method
   ↓
@ExceptionHandler / @RestControllerAdvice — can only catch things thrown from HERE downward
```

**Key implication**: `@RestControllerAdvice` cannot catch exceptions thrown inside the Security filter chain (e.g. missing/invalid JWT), because those exceptions occur *before* `DispatcherServlet`/Spring MVC is ever reached — there's no controller invocation in the call stack yet for `@RestControllerAdvice` to wrap.

## 6. Spring Security: AuthenticationEntryPoint vs @RestControllerAdvice

| Failure type | Where thrown | Who handles it |
|---|---|---|
| Missing/invalid/expired token | Security filter chain | `AuthenticationEntryPoint` |
| Authenticated but not permitted (role/permission) | Security filter chain | `AccessDeniedHandler` |
| Business rule violations (duplicate email, validation, etc.) | Controller/Service layer | `@RestControllerAdvice` |

### AuthenticationEntryPoint
Fires whenever an unauthenticated request hits something requiring authentication (`AuthenticationException` thrown in the filter chain):

```java
public interface AuthenticationEntryPoint {
    void commence(HttpServletRequest request, HttpServletResponse response,
                  AuthenticationException authException) throws IOException, ServletException;
}
```

- Default implementation: `Http403ForbiddenEntryPoint` → bare 403, no body.
- Custom implementation lets you return 401 + a JSON body matching your API's error shape.

```java
@Component
public class JwtAuthenticationEntryPoint implements AuthenticationEntryPoint {
    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response,
                          AuthenticationException authException) throws IOException {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED); // 401
        response.setContentType("application/json");
        Map<String, Object> errors = Map.of("errors", Map.of("token", List.of("is missing")));
        response.getWriter().write(objectMapper.writeValueAsString(errors));
    }
}
```

### Wiring it in via `exceptionHandling(...)`

`exceptionHandling(...)` on `HttpSecurity` tells Spring Security which handler to invoke for which security exception:

```java
.exceptionHandling(ex -> ex
    .authenticationEntryPoint(jwtAuthenticationEntryPoint)   // AuthenticationException → 401
    .accessDeniedHandler(jwtAccessDeniedHandler)             // AccessDeniedException → 403
)
```

## 7. Full traced flow: unauthenticated request to a protected endpoint

Example: `GET /api/user` with no `Authorization` header.

1. `jwtAuthenticationFilter` runs (registered via `addFilterBefore`). No token found → doesn't authenticate → calls `filterChain.doFilter(...)` to let the request continue.
2. `AnonymousAuthenticationFilter` sets an **anonymous** principal in `SecurityContextHolder` (request now has *some* authentication, just not a real one).
3. Request reaches `authorizeHttpRequests` rules. `/api/user` doesn't match `permitAll()` → falls to `anyRequest().authenticated()`.
4. Anonymous principal fails the "authenticated" check → `AuthenticationException` thrown.
5. `ExceptionTranslationFilter` catches it and invokes the configured `AuthenticationEntryPoint`.
6. Without a custom entry point → default `Http403ForbiddenEntryPoint` → bare 403.
   With `JwtAuthenticationEntryPoint` wired in → 401 + `{"errors":{"token":["is missing"]}}`.

## 8. Explained SecurityFilterChain config

```java
@Bean
public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(session -> session
                    .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .exceptionHandling(ex -> ex
                    .authenticationEntryPoint(jwtAuthenticationEntryPoint)
            )
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(basePath + "/users", basePath + "/users/login").permitAll()
                    .anyRequest().authenticated()
            )
            .authenticationProvider(authenticationProvider())
            .addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class);
    return http.build();
}
```

- `.csrf(csrf -> csrf.disable())` — CSRF protection relies on cookies/sessions; irrelevant for a stateless, token-based API.
- `.sessionManagement(STATELESS)` — never create/use `HttpSession`; every request must self-authenticate via its own token. No server-side session store.
- `.exceptionHandling(...)` — registers custom handlers for security exceptions (see above).
- `.authorizeHttpRequests(...)` — authorization rules, evaluated top-to-bottom, first match wins. `permitAll()` for register/login, `authenticated()` for everything else.
  - ⚠️ `requestMatchers(path)` without an HTTP method matches **all** methods on that path — use `requestMatchers(HttpMethod.POST, path)` if you only want to open one verb.
- `.authenticationProvider(...)` — registers the provider (e.g. `DaoAuthenticationProvider`) used to actually verify credentials (used during login, or when your JWT filter constructs/validates an `Authentication`).
- `.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)` — inserts your JWT filter earlier in the chain so it gets first crack at every request, setting the `SecurityContext` before Spring's default filters act.

## 9. Key takeaways / mental models

- **Filter vs Controller**: Filters (incl. all of Spring Security) run *before* Spring MVC/`DispatcherServlet` even starts. Controllers only run *after* filters have let a request through.
- **Two separate error-handling paths are normal**: security failures → `AuthenticationEntryPoint`/`AccessDeniedHandler`; business logic failures → `@RestControllerAdvice`. Make sure both produce the **same JSON error shape**.
- **Socket vs Port**: port = fixed channel number a program listens on; socket = the actual live connection object, one per client, identified by the (client IP, client port, server IP, server port) 4-tuple.
- **Tomcat's core job**: bridge raw HTTP bytes on a socket ↔ Java `HttpServletRequest`/`HttpServletResponse` objects, so the rest of the Java web stack (Spring MVC, your controllers) never has to deal with raw networking.
