# Spring Security JWT Filter — Revision Notes

## 1. The Filter Chain Bug

### Problem
`JwtAuthenticationFilter` never called `filterChain.doFilter()` on the happy path, so the request never reached the controller. This caused a **200 OK with an empty body**.

### Root Cause
```java
try {
    // validate token, set authentication in SecurityContext
    // ❌ no filterChain.doFilter() here — request dies
} catch (Exception e) {
    handlerExceptionResolver.resolveException(...);
    // ❌ no return — would fall through to chain even on error
}
```

### Fix
```java
try {
    // validate token, set authentication
} catch (Exception e) {
    handlerExceptionResolver.resolveException(...);
    return; // ✅ stop — don't continue chain on error
}

filterChain.doFilter(request, response); // ✅ always continue on success
```

### Mental Model
```
Request
  │
  ├── No token → filterChain.doFilter() → next filter → controller
  │                   return (stop this filter)
  │
  └── Has token
            │
            ├── try: validate + set auth
            │         │
            │    ┌─────┴─────┐
            │  success    exception
            │               │
            │          resolveException()
            │               │
            │             return ← chain NOT continued
            │
            └── filterChain.doFilter() ← only on success
```

## 2. Debugging Techniques

### Enable Spring Security Debug Logging
```properties
logging.level.org.springframework.security=DEBUG
logging.level.org.springframework.security.web.FilterChainProxy=DEBUG
```

### Enable Spring MVC Logs
```properties
logging.level.org.springframework.web.servlet.DispatcherServlet=DEBUG
logging.level.org.springframework.web.servlet.mvc.method.annotation.RequestMappingHandlerMapping=TRACE
```

### Enable Security Debug on Config
```java
@EnableWebSecurity(debug = true)
public class SecurityConfiguration { ... }
```

### Drop-in Debug Filter
```java
@Component
@Order(Ordered.LOWEST_PRECEDENCE)
public class DebugFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        System.out.println(">>> Request reached DebugFilter: " + request.getRequestURI());
        chain.doFilter(request, response);
        System.out.println(">>> Response status: " + response.getStatus());
    }
}
```

### Key Things to Search in Logs
| Search Term | What It Tells You |
|---|---|
| `Security filter chain` | Which filters are active |
| `Securing` / `not securing` | Whether security applies to your path |
| `Authentication` | Whether auth is set in SecurityContext |
| `Mapped to` | Whether DispatcherServlet found your controller |
| `No mapping for GET` | URL doesn't match any controller |

## 3. Returning the Token in getCurrentUser

### Problem
The `User` response object needs a token. Regenerating it is wasteful — new `iat` timestamp, unnecessary computation, and confusing for clients.

### Options Compared
| Approach | Problem |
|---|---|
| Generate new token | New `iat`, wasteful, confusing for clients |
| Store token on entity | Defeats JWT stateless design |
| Return original token from header | ✅ Clean and correct |

### Best Practice — Extract from Request in Delegate (Recommended)
Keep HTTP concerns in the HTTP layer. Pass the token down to the service.

```java
@Service
@RequiredArgsConstructor
public class UserApiDelegateImpl implements UserApiDelegate {

    private final UserService userService;
    private final HttpServletRequest request; // Spring injects current request

    @Override
    public ResponseEntity<UserResponse> getCurrentUser() {
        String token = request.getHeader("Authorization").substring(6); // strip "Token "
        UserResponse userResponse = new UserResponse();
        userResponse.setUser(userService.getCurrentUser(token));
        return ResponseEntity.status(HttpStatus.OK).body(userResponse);
    }
}
```

```java
@Service
@RequiredArgsConstructor
public class UserService {

    private final UserMapper userMapper;

    public User getCurrentUser(String token) {
        com.conduit.entity.User user = (com.conduit.entity.User)
            SecurityContextHolder.getContext().getAuthentication().getPrincipal();
        User userDTO = userMapper.toUserDTO(user);
        userDTO.setToken(token);
        return userDTO;
    }
}
```

### Why This is Cleaner
- HTTP concerns (headers, request) stay in the HTTP layer (delegate)
- `UserService` stays pure — just maps data, no request awareness
- `UserService` is easier to unit test — just pass a string

### Alternative — Extract in Service via RequestContextHolder
If you don't want to change the method signature:
```java
HttpServletRequest request = ((ServletRequestAttributes) RequestContextHolder
    .getRequestAttributes())
    .getRequest();
String token = request.getHeader("Authorization").substring(6);
```
This works but mixes HTTP concerns into the service layer — less clean.

## 4. Architecture Summary

```
Request (Authorization: Token <jwt>)
         │
         ▼
JwtAuthenticationFilter
  - Extracts token from header
  - Validates token via JwtService
  - Sets Authentication in SecurityContextHolder
  - Calls filterChain.doFilter() ← critical
         │
         ▼
DispatcherServlet → UserApiController → UserApiDelegateImpl
  - Extracts raw token from header
  - Calls UserService.getCurrentUser(token)
         │
         ▼
UserService
  - Gets User entity from SecurityContext
  - Maps to DTO via UserMapper
  - Sets token on DTO
  - Returns User
```
